# review-triage

レビュー指摘の**仕分け役**。一般的なレビューの観点・深さは外部のスキル／エージェントに委譲し、このスキルは**レビュー源の選択・実行の束ね・分類・ボード化・対応要否の検証・対応記録**を担う。自前で指摘を出すのは、sounding-board のボードやプランファイルを仕様にした**仕様チェック**だけ。

解決する課題は「些末な指摘が重要な指摘と同列に並ぶ」ことと、「件数が多いと 1 件ずつ要否を判断するのが重い」こと。すべての指摘を must / want / nits に仕分けた HTML ボードを作り、続けて各指摘をコードに当たって検証して**推奨（対応／見送り／要判断）と理由**を併記する。ユーザーはボードを見て対応要否を ID で指示する。推奨は判断材料であって決定ではない。

---

## ステップ 1: レビュー対象（base）の確定

レビューするのは **base との merge-base から作業ツリーまで**。コミット済みの変更に加えて、未コミット・未追跡の変更も含める（コミットをユーザーが頼んだときだけ行う運用では、ステップ 9 の修正も未コミットのまま再レビューに回るため）。

- 差分: `git diff --merge-base <base> -- ':/' ':(top,exclude).scratch'`（merge-base から作業ツリーまで。コミット済み＋未コミットで、ステージの有無は問わない。`.scratch/` を git で管理している利用者もいるので、ボードの変更は除く）
- 未追跡ファイル: `git ls-files --others --exclude-standard --full-name -- ':/' ':(top,exclude).scratch'`（差分に出ないので、一覧を渡して全文を見てもらう。リポジトリ全体をルート基準で取り、ボードを置く `.scratch/` は除く）
- コミット一覧: `git log <base>..HEAD --oneline`

以下、この 3 つをまとめて「差分の取り方」と呼ぶ。

1. 引数で base が渡されていればそれを使う
2. 無ければ**必ずユーザーに確認する**。その際、推定候補を添える:
   - `git reflog` の `branch: Created from ...` エントリ
   - `git show-branch` や `git branch --contains` から見える親候補
   - 例: 「比較対象（base）はどれにしますか？ reflog からは `develop` から切られたように見えます」
3. どちらの場合も `git rev-parse --verify <base>` で解決を確認する。解決できなければ（typo・未 fetch など）、推定候補で黙って代用せず、ユーザーに確認し直す
4. `git merge-base <base> HEAD` で共通の祖先が取れることも確かめる。取れなければ（shallow clone・無関係な履歴）止めてユーザーに伝える（shallow なら `git fetch --unshallow` を案内する）
5. base がローカルブランチで、同名の `origin/<base>` がそれより進んでいれば、どちらを使うかをユーザーに確認する（古いローカルの base だと親ブランチの変更が混ざる）

**master を無言で既定にしない**こと。ブランチからブランチを切る運用があるため、base を誤ると親ブランチの変更が差分に混入し、レビュー全体が汚染される。

base 確定後、差分も未追跡ファイルも空ならその旨を伝えて終了する。

## ステップ 2: ボードファイルの決定

レビューごとに 1 ファイル。同じレビューを続けるとき（再レビュー）は、そのファイルを使い回す（→ 2-1）。

置き場所:

1. リポジトリルートの `.scratch/`
2. 無ければ、作るかを 3-4 の問いで一緒に聞く（問 4）。作るが選ばれたら、3-4 の回答を受けてからリポジトリルート直下に作ってそこに置く。`.scratch/` が無ければ、引き継ぐボードや仕様の候補は scratchpad から探す（2-1・3-3）ので、`.scratch/` を作るのが 3-4 の後でも困らない
3. 作らないが選ばれたときは、セッションの scratchpad ディレクトリ。このときはボードを告げる際に、「リポジトリの外に置いたので、別セッションからは再レビューを引き継げない」ことも伝える

`.scratch/` は作業場で、git で管理するかは利用者に任せる。作るかを聞くときの決まり:

- 断られても記録しない。次に起動したときに `.scratch/` が無ければ、また聞く
- 作るのは実ディレクトリだけ（`mkdir <リポジトリルート>/.scratch`）。symlink にするかどうかはユーザーに任せる
- git に無視されているかは確かめず、`.gitignore` なども書き換えない（git で管理するかは利用者が決める）

名前は `<ブランチ名>-<要約>-review.html`（ブランチ名の `/` は `-` に置換する）:

- `<要約>` は今回の変更内容を表す短い英語の kebab-case（2〜4 語。例: `feature-x-retry-on-timeout-review.html`）。ステップ 1 の差分から作る。名前から中身が分かるように、また同じブランチで別の変更をレビューしたときに取り違えないように入れる
- プロジェクトの CLAUDE.md 等に**プランファイル等のプレフィックス命名規則**（チケット番号・Issue 番号など）があれば、先頭にそのプレフィックスを付ける（例: `PROJ-123-feature-x-retry-on-timeout-review.html`・`42-feature-x-retry-on-timeout-review.html`）。プレフィックスは同じブランチの作業中に変わらない値にする（日付のように変わる値では、2-1 で前回のボードが見つからない）
- 名前は初回に決めて固定する。再レビューで要約を作り直して改名しない
- 同じ名前のファイルが既にあれば、聞かずに要約の後ろへ連番を付ける（`…-retry-on-timeout-2-review.html`、それもあれば `-3` …）。接尾辞 `-review.html` は崩さない（2-1 の候補探しに使う。review-triage のボードかどうかの判定は見出しで行い、ファイル名は使わない）

### 2-1. 再レビューかを確かめる

要約は差分から作るので、同じブランチでも毎回同じ言葉になるとは限らない。名前の完全一致では探さず、**候補を探してユーザーに確認する**。

1. 置き場所（`.scratch/`、無ければ scratchpad）の直下（`archive/` などの下は見ない）から、`[<プレフィックス>-]<ブランチ名>-*-review.html` を集める
2. それぞれのヘッダーのブランチと base を今回と照らし合わせ、ブランチが一致するものだけを残す（コミットは修正のたびに増えるので照合に使わない）。前方一致で拾った別ブランチ（`feature` に対する `feature-x-…`）もここで除く。base はヘッダーに書いたハッシュ（ステップ 6）と今回の merge-base で比べる。base の書き方（`main` と `origin/main` など）やハッシュが違うものも黙って落とさず、3 の選択肢に「base が違う（前回: 〈base〉）」と添えて残す
3. 残ったものを更新日時の新しい順に**最大 3 つ**、AskUserQuestion で「〈ファイル名〉を引き継ぐ」（description に見出しの変更内容の一言と最終更新、2 で base が違ったものはその旨）と「新しく作る」から選ばせる。3-4 の問いには入れない（3-4 の「前回実行」の併記は、引き継ぐボードが決まっている前提で書くため）
4. 候補が無ければ聞かずに新しく作る

ブランチと base が同じでも、main 上で日をおいて別の変更をレビューしたときなどは別のレビューである。自動で引き継がないのはこのため。

引き継ぐボードが scratchpad にあるときは、そのまま scratchpad に置く（3-4 の問 4 は出さない）。

引き継ぐと選ばれたら**再レビュー**である。読み込んで以下を引き継ぐ:

- **ヘッダーの「レビュー源」と「仕様」の欄を読み取る**（ステップ 3-4 で「前回実行」を併記するため）。「失敗」と書かれたものは実行済みに数えない
- **見送り済みの指摘は再掲しない**。既存の「見送り」行として残すだけで、新規指摘と混ぜない。ただし対象コードが変わって指摘内容が実質変化した場合のみ、新規 ID で載せる
- 前回「対応する」の指摘が今回検出されなくても、**ステータスは変えない**。未検出はレビュー源の選び直し・出力の揺れ・失敗でも起きるので、解消の証拠にならない。「対応済み」にするのはステップ 9 で修正したときだけ
- 前回「対応済み」の指摘と実質同じ問題が今回も検出されたら、新規 ID で載せ、内容に元の ID を書く（例: 「M1 の修正後も残っている」）
- ID の連番は前回から継続する（同じボードの中で ID を再利用しない）
- **既存指摘の推奨と理由も引き継ぐ**（再検証の対象はステップ 7 の「再レビュー時」を参照）

## ステップ 3: レビュー源の選定

レビュー源は**固定 1 つ ＋ 選択 6 つ**。固定分は常に実行し、選択分は推奨を判定したうえで **AskUserQuestion でユーザーに選ばせる**。固定分と選択分の #3〜#6 は pr-review-toolkit プラグインのエージェントなので、先に入っているかを確かめる（3-0）。

### 3-0. pr-review-toolkit が入っているかを確かめる

Agent ツールで使えるエージェントの一覧に `pr-review-toolkit:` で始まるものがあるかを見る。あればそのまま 3-1 に進む。

無ければ、pr-review-toolkit が無いと #1 の code-reviewer と #3〜#6 を実行できないこと、入れ方（`/plugin install pr-review-toolkit@claude-plugins-official`）を告げ、AskUserQuestion で次の 2 つから選ばせる。

- **やめる**: 入れてから review-triage を起動し直してもらう。ここで終える
- **仕様チェックと security-review だけで続ける**: description に、一般的なコード品質の指摘は出ないことを書く

続けるときは次のとおりにする。

- #1 の code-reviewer は実行しない。ヘッダーのレビュー源欄には「code-reviewer（pr-review-toolkit が無いため実行せず）」と書き、失敗とは書き分ける
- 3-4 の問 1 は出さず、問 2 は #7 security-review を実行するか（「security-review」と「実行しない」の単一選択）にする。問の文に、pr-review-toolkit が無いので #3〜#6 は出していないことを添える
- 仕様チェックも security-review も実行しないことになったら、実行するレビュー源が無いと告げて終える

### 3-1. 固定（常に実行、質問には載せない）

| # | レビュー源 | 備考 |
|---|---|---|
| 1 | `pr-review-toolkit:code-reviewer` エージェント | CLAUDE.md などリポジトリの規約に沿っているかも見る |

**code-reviewer が見ないもの**: 判断ベースのコードスメル（Data Clumps・Feature Envy・Middle Man など、規約に書かれていない設計の癖）は観点に無く、出てこない。また、指摘ごとに自分で付ける確信度（0〜100）が 80 未満のものは報告しない（プラグイン側の設定）。どちらも埋めない方針で、足切りを外す指示も入れない。規約に書かれたことは見るので、CLAUDE.md 以外の規約文書はステップ 4 で探して渡す。

### 3-2. 選択（推奨を判定し、ユーザーが選ぶ）

| # | レビュー源 | 推奨条件 |
|---|---|---|
| 2 | 仕様チェック（自前） | 仕様の候補（3-3）が見つかったとき |
| 3 | `pr-review-toolkit:silent-failure-hunter` | エラーハンドリング・フォールバック・catch 節に触れる差分 |
| 4 | `pr-review-toolkit:type-design-analyzer` | 新しい型・インターフェース定義を含む差分 |
| 5 | `pr-review-toolkit:pr-test-analyzer` | テストの追加・変更、または新機能にテストが無いとき |
| 6 | `pr-review-toolkit:comment-analyzer` | コメント・ドキュメントを大きく追加したとき |
| 7 | `security-review` スキル | 認証・認可・入力処理・秘密情報に触れる差分 |

**`security-review` の制約**: 組み込みのスキルで、base や差分の取り方を渡す手段が無い。差分は自分で取り（origin の既定ブランチとの比較）、未追跡のファイルは見ない。ステップ 1 の base が origin の既定ブランチでないとき・変更が未追跡のときは、3-4 の description にその旨を書く。実行した場合、ステップ 1 の差分・未追跡ファイルに無い箇所への指摘は統合時に除き、除いた件数をレビュー源欄に書く（親ブランチの変更への指摘を混ぜない）。ステップ 1 の base が origin の既定ブランチでないとき・変更が未追跡のときは、見た範囲がステップ 1 と違うこともレビュー源欄に書く（例: 「範囲: origin/main との差分のみ、未追跡は見ていない」。ボードだけを見て、全部見て 0 件だったと取り違えないため）。報告の形は指示できないので、security-review 自身の形式を本体が読み替える。

差分を確認し、#3〜#7 それぞれに推奨／非推奨を付ける。**判定に迷ったら推奨に倒す**（最終判断はユーザーに渡るので、推奨を多めに出しても害は小さい）。

### 3-3. 仕様の候補を集める

仕様チェック（#2）で仕様にするファイルの候補を集める。ブランチと設計ボード・プランファイルを結び付ける仕組みは無いので、**候補を挙げてユーザーに選んでもらう**。

- 探す場所: リポジトリの `.scratch/`（無ければ今のセッションの scratchpad）の直下（`archive/` などの下は見ない）にある sounding-board のボード（`*.html`）とプランファイル（`*.md`）。プロジェクトの CLAUDE.md 等がプランファイルの置き場所を定めていれば、そこも含める
- review-triage のボード（見出しが「レビュー:」で始まるもの。ファイル名では判定しない。今のブランチのものに限らない）と、凍結されていないボード（`<header>` 内のコメントの外に完了バナー `<div class="done">` が無い）は除く。`.done{...}` の CSS 定義はどのボードの `<style>` にもあるので、判定に使わない
- 更新日時の新しい順に**最大 3 つ**。ブランチ名・チケットや Issue の番号・差分のファイル名と関わりがありそうなものを優先する
- 候補が 1 つも無ければ、仕様チェックは問わずに実行しない（宣言で「仕様の候補なし」と伝える）

### 3-4. AskUserQuestion で提示する

**1 回の呼び出しに最大 4 問**を入れる（往復は 1 回で済ませる）。

| 問 | header | 形式 | 選択肢 |
|---|---|---|---|
| 1 | コード品質 | multiSelect | #3 silent-failure-hunter / #4 type-design-analyzer / #5 pr-test-analyzer |
| 2 | 文書・安全 | multiSelect | #6 comment-analyzer / #7 security-review |
| 3 | 仕様チェック | 単一選択 | 仕様の候補（3-3。最大 3 つ）/ 実行しない |
| 4 | 置き場所 | 単一選択 | `.scratch/` を作って置く / 今回は scratchpad に置く（`.scratch/` が無いときだけ。ステップ 2） |

3-0 で pr-review-toolkit 無しで続けるときは、問 1 を出さず、問 2 を変える（3-0）。

選択肢の書き方:

- 推奨するものは **label の末尾に「（推奨）」** を付け、その問の中で先頭に並べる。問 3 では、差分といちばん関わりがありそうな候補を推奨にする
- **description に判定理由を一言**添える（例: 「catch 節の変更あり」「新規の型定義なし」「確定事項に差分のファイルが出てくる」）。非推奨にも理由を書く
- 問 3 の label はファイル名、description には更新日時とボードのテーマ（またはプランの見出し）を書く
- 再レビュー時（ステップ 2）は、前回実行したレビュー源・前回仕様にしたファイルの description に **「前回実行」** を併記する。前回失敗したものは **「前回失敗（理由）」** と書き分ける
- 問 4 の「scratchpad に置く」の description には、別セッションから再レビューを引き継げないことを書く

AskUserQuestion には既定オンの仕組みが無いので、推奨項目もユーザー自身がチェックする。何も選ばれなかった問は「その問のレビュー源は実行しない」と解釈する（問 4 は「scratchpad に置く」と解釈する）。

### 3-5. 宣言して実行へ

固定 1 つ ＋ 選ばれたものを**一言宣言してから**ステップ 4 に進む（例: 「code-reviewer に加えて、仕様チェック（`foo-design.html`）・silent-failure-hunter・security-review を実行します」）。3-0 で pr-review-toolkit 無しで続けるときは、code-reviewer を実行しないことも添える（例: 「pr-review-toolkit が無いので code-reviewer は実行せず、仕様チェック（`foo-design.html`）と security-review を実行します」）。

## ステップ 4: 並列実行

- 実行対象はステップ 3 で確定した「固定 1 つ ＋ ユーザーが選んだもの」だけ。選ばれなかったレビュー源は推奨であっても実行しない
- エージェント（pr-review-toolkit 系と仕様チェック）は**1メッセージにまとめて並列起動**する。各エージェントには base と差分の取り方（ステップ 1。未追跡ファイルの一覧を含む）を渡す
- code-reviewer には、CLAUDE.md 以外の規約文書のパスも渡す。リポジトリのルート・`docs/`・`.github/` の直下で、拡張子を除いた名前が `CONTRIBUTING`・`CODING_STANDARDS`・`STYLEGUIDE`・`STYLE_GUIDE`・`CONVENTIONS` のもの（大文字小文字は問わない）を探し、見つかった分だけを「この規約にも沿っているか見る」と添えて渡す。1 つも無ければ何も渡さない
- スキル（`security-review`）は Skill ツールで呼ぶ。本体のコンテキストで動くので、エージェントを並列起動したあとに呼ぶ
- 各エージェントには「冒頭に見たファイルの一覧、続けて指摘ごとに 対象ファイル:行・問題・根拠 を報告する」よう指示する（分類はこのスキル側で行うので求めない）

### 失敗したレビュー源の扱い

次のどれかに当たったレビュー源は**失敗**として扱い、指摘 0 件とは区別する。

- 起動できなかった（エージェントの呼び出しがエラーになった等。pr-review-toolkit が入っていないことは 3-0 で先に確かめる）
- エラーで終わった、または報告の形になっていない
- 今回の変更を見ていない（見たファイルの一覧にステップ 1 の変更ファイルが 1 つも無い、security-review が取った差分が空だった・今回の変更ファイルを含まない等）。変更ファイルをすべて見るはずの code-reviewer と仕様チェックは、一覧から 1 つでも欠けていれば失敗とする。観点を絞ったエージェント（#3〜#6）は関係のないファイルを開かないのが普通なので、一部が欠けていても失敗にしない
- 仕様チェックが仕様のファイルを読めていない（報告の冒頭の一覧に仕様のファイルが無い）

失敗したものはヘッダーのレビュー源欄に「失敗」と理由を書き分け、ボードを告げるときにチャットでも伝える。失敗と判定したレビュー源が指摘を返していれば、捨てずにボードに載せ、ほかの指摘と同じく検証する（レビュー源欄の「失敗」は、その源に見落としがあり得ることを示す）。固定の code-reviewer が失敗したときは、選択分だけで続けるか止めるかをユーザーに確認する。

### 仕様チェック（自前）の実行

サブエージェント（general-purpose）を 1 つ起動し、ほかのレビュー源と並列に走らせる。外部のレビュー源の結果は渡さない（独立して見る）。渡すもの:

- base と差分の取り方（ステップ 1）
- 仕様にするファイルのパス。sounding-board のボードなら**確定事項（「この設計から作るもの」を含む）と構造（Design Tree またはタイムライン）** を、プランファイルなら手順と変更対象を仕様として読むよう指示する。プランファイルが決定を「ボード参照」で済ませているなら、参照先のボードも読む
- 見る観点: **仕様にあるのに実装されていない**／**仕様と違う形で実装されている**／**仕様に無い変更が入っている**。一般的なコード品質・スタイルは見ない（ほかのレビュー源の担当）
- 報告の形: 冒頭に読んだ仕様のファイルと見たファイルの一覧、続けて指摘ごとに 対象ファイル:行（実装が無い指摘は、入るはずだったファイル）・問題・根拠（仕様のどの決定か。ボードなら Q の ID）。コードは修正しない

## ステップ 5: 統合・分類

### 重複の統合

複数のレビュー源が同じ箇所に実質同じ問題を指摘したら**統合して1件**にし、出典タグを併記する（例: `[spec] [code-reviewer]`）。統合するのは「同じ問題」だけであり、同じ行への別種の指摘は別件のまま残す。

出典タグはレビュー源の短い名前で書く: `code-reviewer` / `spec`（仕様チェック）/ `silent-failure` / `type-design` / `pr-test` / `comment` / `security-review`。ヘッダーのレビュー源欄も同じ名前にする（再レビューで「前回実行」を照らし合わせるため）。

### must / want / nits の判定基準（既定）

| 分類 | 基準 |
|---|---|
| **must** | バグ・セキュリティ・仕様違反・データ破壊。放置するとユーザー影響が出るもの |
| **want** | 設計・保守性・テスト欠落。動くが将来コストになるもの |
| **nits** | 命名・スタイル・好み。どちらでも動作も保守性も変わらないもの |

プロジェクトの CLAUDE.md 等に独自の基準・重み付けがあれば**そちらを優先**する（レビュー開始時に一度確認する）。

### ID の付番

must → `M1, M2, ...` / want → `W1, W2, ...` / nits → `N1, N2, ...`。再レビュー時は既存 ID を変えず、新規指摘に続番を振る。

**分類と ID はここで確定し、以後動かさない。** ステップ 7 の検証で見立てが変わっても、カードの移動や ID の振り直しはしない（ボードは検証前に表示済みで、ユーザーが既に ID を見ているため）。

## ステップ 6: ボード生成

同梱の `template.html` を原型に、単一 HTML として書き出す。構成:

- ヘッダー: 見出しは `レビュー: <ブランチ名> — <変更内容の一言>`（`<title>` も同じ）。一言はファイル名の要約と同じ内容を日本語で短く書き、名前と同じく初回に決めて変えない。見出しの「レビュー:」は 3-3 で review-triage のボードを見分けるのに使い、ブランチは 2-1 の照合と scratch-cleanup（3-2。` — ` の手前までをブランチとして取る）に使うので、この形を崩さない。続けて最終更新（日時と何をしたか）・base（名前と merge-base の短縮ハッシュを必ず併記する。2-1 の照合と scratch-cleanup がどのリポジトリのボードかを見分けるのに使う）・コミット（先頭〜末尾の短縮ハッシュ。0 件ならその旨）・レビュー源（実行したもの。失敗したものは理由つき）・仕様（仕様にしたファイル。仕様チェックを実行したとき）・サマリ（分類ごとの件数と、そのうち未定の件数）・推奨サマリ
- must / want / nits の3セクション。各指摘はカードで、ID・タイトル・対象（`ファイル:行`）・出典タグ・内容（結論1行＋必要なら補足1〜3文）・ステータス・推奨欄を持つ
- ステータスは5値: **未定**（初期値）/ **対応する** / **対応済み** / **見送り** / **保留**
- この時点では検証前なので、新規指摘の推奨欄とヘッダーの推奨サマリは **「検証中」** にしておく

生成したら `open <フルパス>` でデフォルトブラウザに表示し、フルパスを告げる（macOS 以外では `xdg-open` 等に読み替える。開けない環境ならフルパスの告知だけで良い。open は初回と再レビュー開始時のみ。ステータス更新のたびに開き直さない）。あわせて「続けて対応要否を検証します」と一言添え、**そのままステップ 7 に進む**。検証を待たせずに先にボードを出すのは、ユーザーが検証中に指摘を読み始められるようにするため。

## ステップ 7: 対応要否の検証

ボード生成後、**件数に関わらず常に実施する**（ユーザーに実施要否を問わない）。各指摘が本当に対応に値するかをコードに当たって確かめ、推奨と理由をボードに載せる。

### 検証の深さ

**全件、対象コードを実際に読んで検証する**（must / want / nits を問わない）。指摘文だけで判定しない。確認する観点:

- **妥当性** — 指摘は事実か。呼び出し元・周辺コード・既存のガードを見て、誤検知でないか確かめる
- **実害** — 放置した場合に何が起きるか。その経路に実際に到達し得るか
- **修正コスト** — 直す範囲と、直すことによる副作用・リスク

### 推奨の 3 値

| 推奨 | 基準 |
|---|---|
| **対応** | 指摘は事実で、実害または将来コストが修正コストに見合う |
| **見送り** | 誤検知、または事実だが直す価値が修正コスト・リスクに見合わない |
| **要判断** | 仕様の意図・運用方針など、ユーザーにしか決められない情報に依存する。何が分かれば決まるかを理由に書く |

無理にどちらかへ倒さない。判断材料が足りないものは「要判断」にする。

### 理由の書き方

各推奨に**理由を 1 行**添える。検証で確認した事実を書く（「重要なので対応」のような分類の言い換えは不可）。

- **誤検知**は「誤検知 — 根拠」と明記する（例: 「誤検知 — 呼び出し元 `foo.ts:40` で null を弾いており到達しない」）。**誤検知でもカードは消さず、元のセクションに残して「見送り」推奨とする**。黙って削ると、検証側の誤判定で本物の指摘が消えても誰も気付けない
- **分類とのずれ**は理由に明記する（例: 「実害なし、want 相当」「nits とされたが実際に例外になる、must 相当」）。分類と ID は動かさない（ステップ 5）ので、読み替えの手掛かりはこの一行だけになる

### 担い手の切り替え

| 検証対象の件数 | 担い手 |
|---|---|
| 10 件以下（目安） | 本体が直接検証する |
| それを超える | ファイル・ディレクトリ単位などで分割し、サブエージェント（general-purpose）を**1メッセージにまとめて並列起動**して検証させ、本体が結果を統合する |

サブエージェントには担当分の指摘（ID・対象・内容）と base・差分の取り方（ステップ 1）に加え、**上記の「検証の深さ」「推奨の 3 値」「理由の書き方」をそのまま渡す**。基準を渡さないと分割ごとに推奨の粒度がぶれる。「コードは修正しない・ID ごとに 推奨＋理由 1 行 を返す」ことも指示する。統合時、本体は粒度の揃っていない推奨を均す。サブエージェントが返さなかった ID や、推奨・理由が欠けた ID は、本体が対象コードを読んで検証して埋める（「検証中」のまま残さない・指摘文だけで埋めない）。

### ボードへの反映

検証が終わったらボードを上書きする。

- 各カードの推奨欄を「検証中」から **推奨＋理由** に置き換える
- ヘッダーの推奨サマリを内訳にする（例: 「推奨: 対応 5 / 見送り 12 / 要判断 2」）。must / want / nits の件数には誤検知ぶんも含まれたままなので、実質量はこのサマリで伝える
- **ステータスは「未定」のまま変えない**。推奨をステータスに反映するのはユーザーの ID 指示だけ
- `open` し直さず、一行で告知する（例: 「検証完了、ボード更新（推奨: 対応 5 / 見送り 12 / 要判断 2）。リロードしてください」）。「要判断」があれば、何を決めてほしいかをチャットでも短く挙げる

### 再レビュー時

検証するのは次の指摘だけ。それ以外は前回の推奨と理由を引き継ぐ。

- 新規の指摘
- ステータスが「未定」「保留」のままの指摘（修正は未コミットのまま再レビューに回り得るので、対象コードが変わったかはコミットでは判定できない。件数も少ないので毎回再検証する）

ステータス確定済み（対応する／対応済み／見送り）の指摘は再検証しない。確定済みの判断と食い違う推奨を出してもノイズにしかならない。

## ステップ 8: 対応指示の受け付け（ステータス記録のみ）

ユーザーはボードを見て **ID で指示**する（例: 「M1 と W2 対応、N は全部見送り」）。

- ID 指示を受けたら**ボードのステータス更新のみ**行う（「対応する」「見送り」「保留」を反映。ボードは毎回全体を上書きする）。**この時点ではコードを修正しない**
- 更新の告知は一行＋変更点の要約で良い（例: 「ボード更新（M1・W2 → 対応する、N1〜N3 見送り）」）
- 指示が曖昧な場合（例: 「must だけやって」の対象に保留中が混ざる等）は解釈を確認してから反映する
- **推奨の一括承認は設けない**。「推奨どおりで」のような指示は曖昧な指示として扱い、反映する ID と内容を列挙して確認を取ってから反映する（「要判断」は一括の対象にできないので個別に問う）

## ステップ 9: まとめて修正

ユーザーから**明示的な修正指示**（「修正して」「対応を進めて」等）があったら、ステータス「対応する」の指摘を**まとめて修正**する。

- 修正するのはステータス「対応する」の指摘だけ。**自動修正は禁止** — must であっても、推奨が「対応」であっても、承認と修正指示の前にコードへ手を付けない
- 修正の前に、リポジトリにある確認手段（テスト・lint・ビルドなど）を一度走らせて基準を取る。修正後にもう一度走らせ、新たに落ちたものだけを修正による失敗として扱う。どの ID の修正で落ちたか分からなければ、関係しそうな ID をすべて「対応する」に残す
- 確認手段が無いとき、または基準を取る段階で落ちた（ビルドが壊れている・環境のせいで動かない等）ときは、比べられないので無検証になる。無検証で「対応済み」にしたことはチャットで伝え、カードの補足にも「無検証」と書く（ボードは別セッションの再レビューにも使う記録なので、チャットだけでは残らない）
- 修正が終わった指摘はボードのステータスを「対応済み」に更新する
- 修正しきれなかった指摘（一部だけ直せた・方針が成り立たなかった・確認が落ちた）は「対応済み」にせず「対応する」のまま残し、カードの補足に理由を書いて、チャットでも伝える

修正後の再レビューを求められたら、ステップ 1 の base はそのままにステップ 3 以降を再実行し、同じボードを更新する（ステップ 2 の再レビュー規則に従う）。**レビュー源の選択は再レビューでも毎回問う**。修正後の差分は前回と変わるため、前回の選択を無言で引き継がない。

## HTML を書くときの技術的な制約

sounding-board スキルと同じ制約に従う:

- 単一ファイルで完結（CSS はインライン `<style>`、外部リソースは読み込まない。JS は入れない）
- ダークモード対応（`prefers-color-scheme`。テンプレートの CSS 変数で自動的に満たされる）
- `lang="ja"`、`<meta charset="utf-8">`、viewport meta
- 更新は毎回全体を上書き（部分 Edit の継ぎ足しで構造を壊さない）。上書きの前に、いまのボードを読み直す（会話の文脈が要約されたあとに、カードや見送り行を落として書き戻さないため）
- **CSS はテンプレートの `<style>` ブロックを丸ごと複製する**。スクリプトで正規表現抽出する場合は、行頭の `<style>` 行から `</style>` 行までを取る。冒頭コメントなどへの誤一致で CSS の先頭にゴミが混ざると、`:root` の変数定義ごと無効になり、色や線がすべて消える
- **書き出すたびに構造を確かめる**: `grep -c '<style' <file>` と `grep -c '<html' <file>` がどちらも 1 であること（誤抽出時はテンプレートの `<html>`・`<style>` が二重に入る）。満たさなければ作り直してから告知する

## やらないこと

- **仕様チェック以外の自前レビュー**（一般的な観点・深さは外部のレビュー源に委譲する）
- **承認前の修正**（must でも必ずユーザーの ID 指示を待つ）
- **推奨のステータスへの無断反映**（推奨は判断材料。ステータスを動かすのはユーザーの ID 指示だけ）
- **検証による指摘の削除・分類変更・ID 振り直し**（誤検知も見立てのずれも、推奨の理由に書いて残す）
- **検証の省略・指摘文だけでの判定**（件数が少なくても多くても、全件コードを読む）
- **ID 指示への都度修正**（ID 指示時はステータス記録のみ。修正は明示的な修正指示を受けてからまとめて行う）
- 実装の進捗管理（ボードに載せるのは指摘とその対応ステータスまで。作業手順はプランファイル側）
- 見送り済み指摘の蒸し返し
- **選択レビュー源の無断実行**（推奨であっても、ユーザーが選ばなかったものは走らせない。固定の code-reviewer のみ例外）
- 前回の選択の無言引き継ぎ（再レビューでも毎回問う）
- Artifact としての公開（ローカルファイルに留める）
