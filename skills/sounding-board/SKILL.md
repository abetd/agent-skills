# sounding-board

ユーザーの**壁打ちの相手**になる。問いを出してラウンドを回し、答えを受けて次の問いを出す。その過程を 1 テーマ 1 ファイルの HTML ボードに毎回上書きで残し、「今どこまで決まったか」「次に何を問われるか」を常に見える状態に保つ。

問いを出すのも、板に残すのもこのスキルの役割。ほかの対話スキル（問いを出してユーザーと詰めていくスキル）とは同時に使わない（問う役が二重になる）。

## 何のためにあるか

- チャットは時系列で流れて消える。Markdown も上から下への線形記法で、**状態**（確定／未確定）と**構造**（どの決定がどれにぶら下がるか）を表現できない
- 最後にまとめるだけなら Markdown のプランファイルと変わらない。**都度更新して未回答の問いも載せる**のが肝

## ステップ 1: 起動と出力先の決定

### 1-1. テーマを確定する

引数でテーマが渡されていればそれを使う。無ければ会話の文脈から推測して一言で確認する（「〈テーマ〉について詰めていきますね」）。確認のためだけに話を止めない。

### 1-2. 出力ディレクトリを決める

以下の順で判定する。

1. リポジトリルート（`git rev-parse --show-toplevel`）に `.scratch/` があればそこ
2. git リポジトリの中で `.scratch/` が無ければ、AskUserQuestion で作るかを聞く。選択肢は「`.scratch/` を作って置く」と「今回は scratchpad に置く」の 2 つ。作るが選ばれたら、リポジトリルート直下に作ってそこに置く
3. 作らないが選ばれたとき・git リポジトリの外のときは、セッションの scratchpad ディレクトリ

`.scratch/` は作業場で、git で管理するかは利用者に任せる。優先するのは、**別セッションから再開できるようにするため**。scratchpad はセッション ID 込みのパスに掘られるので、セッションが変わると辿り着けない。scratchpad に置いたときは、初回の告知（1-5）で「リポジトリの外に置いたので、別セッションからは再開できない」ことも伝える。

作るかを聞くときの決まり:

- 断られても記録しない。次に起動したときに `.scratch/` が無ければ、また聞く
- git リポジトリの外では聞かない（作る場所の基準が無い）
- 作るのは実ディレクトリだけ（`mkdir <リポジトリルート>/.scratch`）。symlink にするかどうかはユーザーに任せる
- git に無視されているかは確かめず、`.gitignore` なども書き換えない（git で管理するかは利用者が決める）

### 1-3. ファイル名を決める

プロジェクトの CLAUDE.md 等に**プランファイルの命名規則**があればそれに従う（例: `PROJ-123-<説明>` → `PROJ-123-<説明>.html`、`42-<説明>` → `42-<説明>.html`）。無ければ `<テーマのkebab-case>.html`。

### 1-4. 既存ファイルがあれば読む（別セッションからの再開）

同名ファイルが既にあれば、**新規作成せず読み込んでから続きを書く**。ファイルが長い場合は全部読まず、**確定事項・Design Tree（または相当する構造部分）と「回答待ち」項目だけを先に読む**。過去の Q&A ログは、問いを考える段階では参照が必要になった時点で読めばよい。ただし**最初の更新を書き出す前には全文を読む**。更新は全体の上書きなので、読んでいない部分は書き戻せずに消える。

ヘッダーのテーマが今回の話題と明らかに違う（名前が偶然一致した別テーマ）なら、続きを書かずに、別の名前で作るかをユーザーに確認する。

`<header>` 内のコメントの外に完了バナー（`<div class="done">`）が置かれていれば、その議論は凍結済み（→ ステップ 7）。テンプレートは凍結前でもコメントの中にバナーを持つので、コメントの中にあるものは数えない。続けたいことがあれば、凍結を解くか、新しいテーマのボードを作るかをユーザーに確認する。凍結を解くときは完了バナーをまたコメントに戻す（コメントの外に残すと review-triage が凍結済みとして仕様の候補に挙げ、scratch-cleanup も凍結前のボードとして残さなくなる）。

### 1-5. 初期ファイルを生成する

同梱の `template.html` を原型として使う。テンプレートは**骨格 CSS ＋ 固定順のセクション ＋ セクション内の部品カタログ**という構成なので、CSS はそのまま流用し、部品は必要な型だけを残して不要なものを削る。

生成したら、フルパスを告げる（フルパスを告げるのは初回生成時と、別セッションからの再開時だけ）。あわせて `open <フルパス>` を実行し、デフォルトブラウザで表示する（macOS 以外では `xdg-open` 等に読み替える。開けない環境ならフルパスの告知だけで良い）。

`open` を実行するのは**初回生成時と、別セッションからの再開時（1-4）のみ**。以降の更新は同一ファイルの上書きなので、ユーザーがブラウザをリロードすれば反映される。更新のたびに `open` し直すとブラウザにフォーカスが奪われてノイズになる。

## ステップ 2: ボードの構成

### 2-1. セクションの並び（固定）

どの型の議論でも、セクションは次の順に並べる。

| # | セクション | 中身 |
|---|---|---|
| 1 | **確定事項** | 課題を 1 行 ＋ 確定した決定の一覧。実装に繋がる議論なら、凍結時に「この設計から作るもの」もここに置く |
| 2 | **構造** | Design Tree（意思決定・設計）またはタイムライン（調査・障害対応） |
| 3 | **Q&A の補足** | 調べて分かったこと・比較表・仮説と検証・フロー図など、問いに答えるための材料 |
| 4 | **Q&A ログ** | Round ごとの問いと答え。古い Round が上、最新の Round が末尾 |

壁打ち中は末尾の最新 Round が中心になり、上へスクロールすると、その Round に関わる材料・構造・確定事項を遡れる。ページを開いたときの表示位置は変えない（JS は入れない）。

### 2-2. 議論の型に応じて部品を選ぶ

| 議論の型 | 構造 | Q&A の補足 |
|---|---|---|
| 意思決定・設計 | Design Tree | 調べて分かったこと・比較表 |
| 調査・障害対応 | タイムライン | 仮説と検証結果の表 |
| 比較検討 | Design Tree | 比較表 ＋ 評価軸の明示 |
| 上記に当てはまらない | **部品を自由に組み合わせてよい**（並びは 2-1 を守る） | |

対応表は出発点であって拘束ではない。ただし指針が無いと何でも決定木で書いてしまうので、**まず型を判定してから書き始める**こと。議論の途中で型が変わった（設計の議論が調査に転じた等）なら、部品を足すか差し替える。

## ステップ 3: 問いの出し方

### 3-1. 問う前に調べる

コード・ファイル・既存実装・環境を調べれば分かることは問わない。調べた事実は「Q&A の補足」の「調べて分かったこと」に載せ、問いの前提にする。

### 3-2. 1 Round の組み立て

- 問いは **AskUserQuestion** で出す。1 回に **1〜4 問**
- 同じ Round に入れるのは、**互いに独立していて今答えられる問い**だけ。前の答えで中身が変わる問いは後の Round に回し、構造には「未着手」で載せておく
- 各問いに選択肢を 2〜4 つ付ける。推奨できるものは label の末尾に「（推奨）」を付けて先頭に置く。description にはトレードオフや「選ぶと後で何が縛られるか」を短く書く
- 推奨の根拠が立たない問い（好み・ユーザーにしか分からない事情）は推奨を付けない

### 3-3. 答えが選択肢に収まらなかったとき

質問返し・別の案・迷いが返ってきたら、**確定扱いにしない**。

- 「反応」として Q&A ログに記録する
- 質問には調べて答える。別の案には、推奨との違いと、それを選ぶと何が変わるかの見解を返す
- 前提が決まっていないせいで答えにくい問いだと分かったら、問いを分けるか、前提の問いを先に立てる（構造では元の問いの子として載せる）
- そのうえで改めて問う

ユーザーの答えが前の決定と食い違うときは、黙って上書きせず、どの決定を修正することになるかを示して確認する。

### 3-4. 1 Round の流れ

1. 答えをボードに反映する（確定・却下・反応・判明した事実）
2. 次の問いを「回答待ち」としてボードに載せる
3. チャットで一行の告知（→ ステップ 6）と、確定したことが後で何を縛るかの要約を短く書く
4. AskUserQuestion で問う

**ボードを更新してから問う**。問いが先に出ると、ボードを見ても今何を問われているかが分からない。

## ステップ 4: 更新トリガー

**以下のいずれかが起きる応答の直前に更新する。どちらも無い応答では更新しない。**

1. **決定・事実が確定した**（板の既存記述が古くなる）
2. **新しい問いをユーザーに投げる**（「回答待ち」ノードが増える）

具体的には:

- ユーザーが問いに答えた／方針を選んだ／選択肢を却下した／選択肢以外の反応を返した
- 調査で事実が判明した（ファイルの実体、既存実装の挙動、環境の制約など）
- これから新しい問い・検討事項を提示する ── **問いを投げる前に「回答待ち」ノードとして板に載せてから問う**。確定が何も無くても更新する
- 前の決定が修正された

更新しない例: 相槌、途中経過の報告、回答を求めず考えを整理しているだけの応答、実装作業そのものの進捗。

Round が切り替わって次の問いを出す時点は、前 Round の確定（トリガー 1）と新しい問い（トリガー 2）が同時に起きるので、必ず更新してから問う。

## ステップ 5: 書く内容のルール

### 5-1. 二層構造にする

**結論は一行、背景は補足ブロック**。読み飛ばせるが、必要なら深く読める形にする。逐語ログは持たない ── 削るのは会話の冗長さであって、理解に必要な文脈ではない。

### 5-2. 確定事項は書き直す

確定事項は**いまの合意内容**を表す一覧なので、Round のたびに追記ではなく書き直す。決定が修正されたら古い内容は消し、経緯は Q&A ログの補足に残す。ここには「何が決まったか」だけを短く書く。

review-triage の仕様チェックは、確定事項と構造（Design Tree またはタイムライン）を仕様として読む。ここが古いと仕様チェックもずれる。

### 5-3. 補足ブロックを書く条件

以下のいずれかに該当するときは**必須**。該当しなければ書かない（自明な決定に説明を付けると読む量が無駄に増える）。

1. 却下した選択肢がある
2. トレードオフがある
3. 前の決定を修正した

長さは **1〜3 文**。内容は「なぜ選んだか」ではなく **「その選択が後で何を縛るか」** に寄せる。前者は選択肢の提示文に既に書かれていて重複する。

### 5-4. 図を入れる条件

**構造・流れ・比較のいずれかが対象に含まれるときのみ**。装飾目的では入れない。テンプレートのフロー図・ツリー・表で足りることが多い。足りなければインライン SVG を書いてよい（外部リソースは読み込まない）。

### 5-5. 直近の変更を明示する

**今回の更新で変わった項目にだけ `NEW` マークを付け、次の更新で外す**。全項目にラウンド番号を振るのは視覚的にうるさく、古い番号は役に立たない。

チャット側の要約は「チャットを見ている今」にしか効かない。別セッションから再開したとき、**ファイル単体で直近の動きが分かる**必要があるため、このマークは省略しない。

### 5-6. 未回答の項目を必ず載せる

まだ答えが出ていない問いも「回答待ち」ステータスで構造に載せる。**これから何が問われるか**が見えることで、回答する側も残量を把握できる。ここを省くと、このスキルは事後まとめと変わらなくなる。

## ステップ 6: 更新の告知

- **初回生成時と、別セッションからの再開時（1-4）だけ**フルパスを出し、`open` でブラウザ表示する（→ 1-5）
- **以降は一行 ＋ 変更点の要約**（例: 「ボードを更新（Q7 を確定、Q8〜Q9 を追加）」）。ブラウザ側はリロードで最新になる

毎回フルパスを出すのはノイズ。無言で更新するのも駄目 ── 何が動いたか分からず、結局 HTML を開いて差分を探すことになる。

---

## ステップ 7: 合意到達後の扱い

**回答待ちと未着手の項目がどちらも空になったら、ヘッダーに完了バナー（`.done`）を置いて凍結する。** 未着手が残っているなら、問いとして出すか、ユーザーと合意して範囲外にするまで凍結しない。範囲外にした論点は、Design Tree のノードを消さずに確定（s）にし、答えに「範囲外（却下）— 理由」と書く。凍結したボードは review-triage の仕様の候補になるので、詰め残しがあるまま凍結しない。

- 完了バナー（テンプレートではコメントにしてある）をヘッダーに置き、確定項目数と「回答待ち・未着手ともに空」であることを書く
- 実装に繋がる議論なら、確定事項に「この設計から作るもの」を置く
- チャットで作るものを要約し、**実装を始めてよいかを尋ねる**。許可が出るまで実装に入らない
- **以降の実装進捗はこの HTML に追記しない**。進捗はプランファイル側で管理する

## プランファイル（.md）との関係

両者は読む目的が違う。

| | 読む目的 | 内容 |
|---|---|---|
| sounding-board の HTML | **合意したか確認する** | 決定・却下理由・未解決の問い |
| プランファイル | **実装しながら参照する** | 手順・変更対象ファイル |

HTML を先に作り、**プランファイルはそれを参照する**。プランファイルを書くときは冒頭に HTML へのリンクを置き、決定事項は「詳細は sounding-board のボード参照」と書いて短く保つ。

## HTML を書くときの技術的な制約

- **単一ファイルで完結させる**。CSS はインライン `<style>`、外部リソース（CDN、Web フォント、画像）は読み込まない。JS は入れない
- **ダークモード対応**（`prefers-color-scheme`）。テンプレートの CSS 変数を使えば自動的に満たされる
- `lang="ja"`、`<meta charset="utf-8">`、viewport meta を付ける
- 毎回**全体を上書き**する。部分的な Edit で継ぎ足すと構造が壊れやすい。既存内容は読み込んだうえで書き直す
- **CSS はテンプレートの `<style>` ブロックを丸ごと複製する**。スクリプトで正規表現抽出する場合は、行頭の `<style>` 行から `</style>` 行までを取る。冒頭コメントなどへの誤一致で CSS の先頭にゴミが混ざると、`:root` の変数定義ごと無効になり、色や線がすべて消える
- **書き出すたびに構造を確かめる**: `grep -c '<style' <file>` と `grep -c '<html' <file>` がどちらも 1 であること（誤抽出時はテンプレートの `<html>`・`<style>` が二重に入る）。満たさなければ作り直してから告知する

## やらないこと

- 許可前の実装（合意しても、実装を始めるのはユーザーの許可を得てから）
- ほかの対話スキルとの同時起動
- 調べれば分かることを問う
- 選択肢以外の反応を確定として扱う
- 実装の進捗管理（→ プランファイル）
- 逐語ログの保持
- Artifact としての公開（ローカルファイルに留める）
