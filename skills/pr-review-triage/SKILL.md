# pr-review-triage

他の人の PR を、**レビューアとして**仕分ける。一般的なレビューの観点・深さは外部のスキル／エージェントに委譲し、このスキルは**レビュー源の選択・実行の束ね・分類・ボード化・コメントするかの検証・コメントの下書き**を担う。自前で指摘を出すのは、ユーザーが渡した仕様での**仕様チェック**だけ。

自分のブランチを仕分けて自分で直す review-triage と、次の点が違う。

| | review-triage | pr-review-triage |
|---|---|---|
| 対象 | base との merge-base から作業ツリーまで（未コミットも含む） | base との merge-base から、checkout 済みの HEAD まで（未コミットは含めない） |
| 仕様 | `.scratch/` のボード・プランから候補を選ぶ | ユーザーが渡したもの（ファイルのパス・貼り付けた本文） |
| 推奨 | 対応／見送り／要判断 | コメントする／コメントしない／要判断 |
| 出口 | ID で決めた指摘を自分でまとめて直す | ID で「コメントする」にした指摘に PR コメントの下書きを作る。直さない・投稿しない |

PR のコメントの投稿は人がする。`gh` などホスティングの CLI は使わず、PR の説明文やコメントも取りに行かない（Bitbucket・GitLab などでも同じように使えるようにするため）。

---

## ステップ 1: レビュー対象の確定

PR のブランチは、ユーザーが**事前に checkout しておく**。このスキルは worktree を作らず、手元の作業ツリーがその PR の head になっているかを確かめるだけ。pr-review-toolkit のエージェントは周辺のコードを作業ツリーから読むので、作業ツリーが head でないと違う版のコードを見てしまう。

### 1-1. 作業ツリーを確かめる

次のどれかに当たったら、**止めて**理由と直し方を伝える。

1. `git branch --show-current` が空（detached HEAD）: PR のブランチを、ブランチとして checkout してもらう（見出しのブランチ名と upstream の照合に使う）
2. 未コミットの変更がある: `git status --porcelain -- ':/' ':(top,exclude).scratch'` が空でない（未追跡のファイルも含む。ボードを置く `.scratch/` は除く）。自分の作業中の変更なら、退避してもらう
3. upstream が無い: `git rev-parse --abbrev-ref @{u}` が失敗する。upstream を張って checkout し直してもらう（fork からの PR なら、作者の remote を足して、その追跡ブランチで checkout する）
4. HEAD が upstream と一致しない: `git rev-parse HEAD` と `git rev-parse @{u}` が違う。`git rev-list --left-right --count HEAD...@{u}` で ahead / behind を添えて伝え、合わせてもらう

`git fetch` はしない。照合するのは手元の remote-tracking の ref とだけなので、作者の最新の push を取り込んでいるかは、ユーザーに任せる。1-1 を通ったら、「fetch はしていないので、最新の push を取り込んだかはご自身で確かめてください」と一言添える。

### 1-2. base を確かめる

1. 引数で base が渡されていればそれを使う
2. 無ければ**推定せずにユーザーに聞く**（PR のブランチを checkout しただけでは reflog に親が残らないので、review-triage の推定は当たらない）。例: 「この PR のマージ先（base）はどれですか？」
3. どちらの場合も `git rev-parse --verify <base>` で解決を確認する。解決できなければ、ユーザーに確認し直す
4. `git merge-base <base> HEAD` で共通の祖先が取れることも確かめる。取れなければ（shallow clone・無関係な履歴）止めてユーザーに伝える（shallow なら `git fetch --unshallow` を案内する）
5. base がローカルブランチで、同名の `origin/<base>` がそれより進んでいれば、どちらを使うかをユーザーに確認する（古いローカルの base だと、マージ先の変更が差分に混ざる）

**master を無言で既定にしない**こと。base を誤ると、PR に含まれない変更が差分に混入し、レビュー全体が汚染される。

### 1-3. 差分の取り方

- 差分: `git diff --merge-base <base> HEAD -- ':/' ':(top,exclude).scratch'`（merge-base から HEAD まで。`.scratch/` を git で管理している利用者もいるので、ボードの変更は除く）
- コミット一覧: `git log <base>..HEAD --oneline -- ':/' ':(top,exclude).scratch'`

1-1 で作業ツリーがきれいなことを確かめているので、未追跡のファイルは無い。以下、この 2 つをまとめて「差分の取り方」と呼ぶ。

差分が空ならその旨を伝えて終了する。

## ステップ 2: ボードファイルの決定

レビューごとに 1 ファイル。作者が push した後にもう一度見るとき（再レビュー）は、そのファイルを使い回す（→ 2-1）。

置き場所:

1. リポジトリルートの `.scratch/`
2. 無ければ、作るかを 3-4 の問いで一緒に聞く（問 4）。作るが選ばれたら、3-4 の回答を受けてからリポジトリルート直下に作ってそこに置く。`.scratch/` が無ければ、引き継ぐボードは scratchpad から探す（2-1）ので、`.scratch/` を作るのが 3-4 の後でも困らない
3. 作らないが選ばれたときは、セッションの scratchpad ディレクトリ。このときはボードを告げる際に、「リポジトリの外に置いたので、別セッションからは再レビューを引き継げない」ことも伝える

`.scratch/` は作業場で、git で管理するかは利用者に任せる。作るかを聞くときの決まり:

- 断られても記録しない。次に起動したときに `.scratch/` が無ければ、また聞く
- 作るのは実ディレクトリだけ（`mkdir <リポジトリルート>/.scratch`）。symlink にするかどうかはユーザーに任せる
- git に無視されているかは確かめず、`.gitignore` なども書き換えない（git で管理するかは利用者が決める）

名前は `<ブランチ名>-<要約>-pr-triage.html`（ブランチ名の `/` は `-` に置換する）:

- `<要約>` は PR の変更内容を表す短い英語の kebab-case（2〜4 語。例: `feature-x-retry-on-timeout-pr-triage.html`）。ステップ 1 の差分から作る
- プロジェクトの CLAUDE.md 等に**プランファイル等のプレフィックス命名規則**（チケット番号・Issue 番号など）があれば、先頭にそのプレフィックスを付ける（例: `PROJ-123-feature-x-retry-on-timeout-pr-triage.html`）。プレフィックスは同じ PR のレビュー中に変わらない値にする
- 名前は初回に決めて固定する。再レビューで要約を作り直して改名しない
- 同じ名前のファイルが既にあれば、聞かずに要約の後ろへ連番を付ける（`…-retry-on-timeout-2-pr-triage.html`、それもあれば `-3` …）。接尾辞 `-pr-triage.html` は崩さない（2-1 の候補探しに使う。また、review-triage のボード（`-review.html`）とはこの接尾辞で見分ける。見出しはどちらも `レビュー:` で始まる）

### 2-1. 再レビューかを確かめる

1. 置き場所（`.scratch/`、無ければ scratchpad）の直下（`archive/` などの下は見ない）から、`[<プレフィックス>-]<ブランチ名>-*-pr-triage.html` を集める
2. それぞれのヘッダーのブランチと base を今回と照らし合わせ、ブランチが一致するものだけを残す（コミットは push のたびに増えるので照合に使わない）。前方一致で拾った別ブランチ（`feature` に対する `feature-x-…`）もここで除く。base はヘッダーに書いたハッシュ（ステップ 6）と今回の merge-base で比べる。base の書き方やハッシュが違うものも黙って落とさず、3 の選択肢に「base が違う（前回: 〈base〉）」と添えて残す（作者がマージ先を取り込むと merge-base は動く）
3. 残ったものを更新日時の新しい順に**最大 3 つ**、AskUserQuestion で「〈ファイル名〉を引き継ぐ」（description に見出しの変更内容の一言と最終更新、2 で base が違ったものはその旨）と「新しく作る」から選ばせる。3-4 の問いには入れない
4. 候補が無ければ聞かずに新しく作る

引き継ぐボードが scratchpad にあるときは、そのまま scratchpad に置く（3-4 の問 4 は出さない）。

引き継ぐと選ばれたら**再レビュー**である。読み込んで以下を引き継ぐ:

- **ヘッダーの「レビュー源」と「仕様」の欄を読み取る**（3-4 で「前回実行」を併記し、前回の仕様を示すため）。「失敗」と書かれたものは実行済みに数えない
- **投稿済み・コメントしないの指摘は再掲しない**。既存のカードとして残すだけで、新規指摘と混ぜない
  - 投稿済みの指摘と実質同じ問題が今回も検出されたら、新規 ID は作らず、元のカードに「push 後も残っている（〈HEAD の短縮ハッシュ〉）」と書き足すだけにする。下書きも作らない（作者への再指摘は、ユーザーが元のコメントへ PR 上で返信する）
  - コメントしないの指摘は、対象コードが変わって指摘内容が実質変化した場合のみ、新規 ID で載せる
- 未定・保留・コメントするの指摘と実質同じ問題が今回も検出されたら、新規 ID は作らず、既存のカードとして扱う（ステップ 7 の「再レビュー時」で再検証する）
- 前回「コメントする」の指摘が今回検出されなくても、**ステータスは変えない**。未検出はレビュー源の選び直し・出力の揺れ・失敗でも起きるので、解消の証拠にならない（解消したかはステップ 7 で再検証する）
- ID の連番は前回から継続する（同じボードの中で ID を再利用しない）
- **既存指摘の推奨と理由、下書きも引き継ぐ**（再検証の対象はステップ 7 の「再レビュー時」を参照）

## ステップ 3: レビュー源の選定

レビュー源は**固定 1 つ ＋ 選択 6 つ**。固定分は常に実行し、選択分は推奨を判定したうえで **AskUserQuestion でユーザーに選ばせる**。固定分と選択分の #3〜#6 は pr-review-toolkit プラグインのエージェントなので、先に入っているかを確かめる（3-0）。

### 3-0. pr-review-toolkit が入っているかを確かめる

Agent ツールで使えるエージェントの一覧に `pr-review-toolkit:` で始まるものがあるかを見る。あればそのまま 3-1 に進む。

無ければ、pr-review-toolkit が無いと #1 の code-reviewer と #3〜#6 を実行できないこと、入れ方（`/plugin install pr-review-toolkit@claude-plugins-official`）を告げ、AskUserQuestion で次の 2 つから選ばせる。

- **やめる**: 入れてから pr-review-triage を起動し直してもらう。ここで終える
- **仕様チェックと security-review だけで続ける**: description に、一般的なコード品質の指摘は出ないことを書く

続けるときは次のとおりにする。

- #1 の code-reviewer は実行しない。ヘッダーのレビュー源欄には「code-reviewer（pr-review-toolkit が無いため実行せず）」と書き、失敗とは書き分ける
- 3-4 の問 1 は出さず、問 2 は #7 security-review を実行するか（「security-review」と「実行しない」の単一選択）にする。問の文に、pr-review-toolkit が無いので #3〜#6 は出していないことを添える
- 仕様チェックも security-review も実行しないことになったら、実行するレビュー源が無いと告げて終える

### 3-1. 固定（常に実行、質問には載せない）

| # | レビュー源 | 備考 |
|---|---|---|
| 1 | `pr-review-toolkit:code-reviewer` エージェント | CLAUDE.md などリポジトリの規約に沿っているかも見る |

**code-reviewer が見ないもの**: 判断ベースのコードスメル（Data Clumps・Feature Envy・Middle Man など、規約に書かれていない設計の癖）は観点に無く、出てこない。また、指摘ごとに自分で付ける確信度（0〜100）が 80 未満のものは報告しない（プラグイン側の設定）。どちらも埋めない方針で、足切りを外す指示も入れない。規約に書かれたことは見るので、CLAUDE.md 以外の規約文書はステップ 4 で探して渡す。

### 3-2. 選択（推奨を判定し、ユーザーが選ぶ）

| # | レビュー源 | 推奨条件 |
|---|---|---|
| 2 | 仕様チェック（自前） | 3-4 の問 3 で仕様を渡されたら実行する（3-3） |
| 3 | `pr-review-toolkit:silent-failure-hunter` | エラーハンドリング・フォールバック・catch 節に触れる差分 |
| 4 | `pr-review-toolkit:type-design-analyzer` | 新しい型・インターフェース定義を含む差分 |
| 5 | `pr-review-toolkit:pr-test-analyzer` | テストの追加・変更、または新機能にテストが無いとき |
| 6 | `pr-review-toolkit:comment-analyzer` | コメント・ドキュメントを大きく追加したとき |
| 7 | `security-review` スキル | 認証・認可・入力処理・秘密情報に触れる差分 |

**`security-review` の制約**: 組み込みのスキルで、base や差分の取り方を渡す手段が無い。差分は自分で取る（origin の既定ブランチとの比較）。ステップ 1 の base が origin の既定ブランチでないときは、3-4 の description にその旨を書く。実行した場合、ステップ 1 の差分に無い箇所への指摘は統合時に除き、除いた件数をレビュー源欄に書く（PR に含まれない変更への指摘を混ぜない）。base が origin の既定ブランチでないときは、見た範囲がステップ 1 と違うこともレビュー源欄に書く（例: 「範囲: origin/main との差分のみ」）。報告の形は指示できないので、security-review 自身の形式を本体が読み替える。

差分を確認し、#3〜#7 それぞれに推奨／非推奨を付ける。**判定に迷ったら推奨に倒す**（最終判断はユーザーに渡るので、推奨を多めに出しても害は小さい）。

### 3-3. 仕様の受け取り

レビューアの手元には、作者が検討に使ったボードやプランが無いことが多い。`.scratch/` から候補を探すことはせず、**仕様にするものがあるかを 3-4 の問 3 で聞いて、渡されたものだけを使う**。

- 問 3 は multiSelect で「無し」「ファイルのパスを渡す」「本文を貼る」の 3 つ。仕様にできるのは、PR の説明文・Issue・作者から受け取ったボードやプランなど
- 「ファイルのパスを渡す」「本文を貼る」が選ばれたら、3-4 の回答の後に、パスと本文をチャットで受け取る。パスは複数受け付け、貼り付けとも一緒に使える
- 何も選ばれなかったとき・「無し」だけのときは、仕様チェックを実行しない
- 「無し」と「ファイルのパスを渡す」「本文を貼る」を一緒に選ばれたら、パス・本文の方を優先して受け取りに進む。受け取るときに「仕様が無ければ『無し』と返してください」と添える
- パスが読めなければ（存在しない等）、そのパスを告げて渡し直してもらう
- 再レビューでも毎回聞き直す。問の文に前回の仕様（ヘッダーの仕様欄）を示す（例: 「前回の仕様: `foo-design.html`・貼り付けの本文（冒頭の一文: 「リトライ回数を設定できるようにする」）」）。貼り付けた本文はボードに残らないので、同じ仕様を使うなら貼り直してもらう

### 3-4. AskUserQuestion で提示する

**1 回の呼び出しに最大 4 問**を入れる（往復は 1 回で済ませる）。

| 問 | header | 形式 | 選択肢 |
|---|---|---|---|
| 1 | コード品質 | multiSelect | #3 silent-failure-hunter / #4 type-design-analyzer / #5 pr-test-analyzer |
| 2 | 文書・安全 | multiSelect | #6 comment-analyzer / #7 security-review |
| 3 | 仕様チェック | multiSelect | 無し / ファイルのパスを渡す / 本文を貼る（3-3） |
| 4 | 置き場所 | 単一選択 | `.scratch/` を作って置く / 今回は scratchpad に置く（`.scratch/` が無いときだけ。ステップ 2） |

3-0 で pr-review-toolkit 無しで続けるときは、問 1 を出さず、問 2 を変える（3-0）。

選択肢の書き方:

- 推奨するものは **label の末尾に「（推奨）」** を付け、その問の中で先頭に並べる。問 3 には推奨を付けない（仕様があるかはユーザーにしか分からない）
- **description に判定理由を一言**添える（例: 「catch 節の変更あり」「新規の型定義なし」）。非推奨にも理由を書く
- 再レビュー時（ステップ 2）は、前回実行したレビュー源の description に **「前回実行」** を併記する。前回失敗したものは **「前回失敗（理由）」** と書き分ける
- 問 4 の「scratchpad に置く」の description には、別セッションから再レビューを引き継げないことを書く

AskUserQuestion には既定オンの仕組みが無いので、推奨項目もユーザー自身がチェックする。何も選ばれなかった問は「その問のレビュー源は実行しない」と解釈する（問 4 は「scratchpad に置く」と解釈する）。受け取った仕様は、すべて 1 つの仕様チェックに渡す（ステップ 4）。

### 3-5. 宣言して実行へ

固定 1 つ ＋ 選ばれたものを**一言宣言してから**ステップ 4 に進む。仕様チェックには、受け取った仕様をすべて並べる（例: 「code-reviewer に加えて、仕様チェック（`foo-design.html`・貼り付けの本文）・silent-failure-hunter を実行します」）。3-0 で pr-review-toolkit 無しで続けるときは、code-reviewer を実行しないことも添える。

## ステップ 4: 並列実行

- 実行対象はステップ 3 で確定した「固定 1 つ ＋ ユーザーが選んだもの」だけ。選ばれなかったレビュー源は推奨であっても実行しない
- エージェント（pr-review-toolkit 系と仕様チェック）は**1メッセージにまとめて並列起動**する。各エージェントには base と差分の取り方（ステップ 1）を渡す
- code-reviewer には、CLAUDE.md 以外の規約文書のパスも渡す。リポジトリのルート・`docs/`・`.github/` の直下で、拡張子を除いた名前が `CONTRIBUTING`・`CODING_STANDARDS`・`STYLEGUIDE`・`STYLE_GUIDE`・`CONVENTIONS` のもの（大文字小文字は問わない）を探し、見つかった分だけを「この規約にも沿っているか見る」と添えて渡す。1 つも無ければ何も渡さない
- スキル（`security-review`）は Skill ツールで呼ぶ。本体のコンテキストで動くので、エージェントを並列起動したあとに呼ぶ
- 各エージェントには「冒頭に見たファイルの一覧、続けて指摘ごとに 対象ファイル:行・問題・根拠 を報告する」よう指示する（分類はこのスキル側で行うので求めない）。削除された行への指摘は、base 側の行番号であることを書き分けるよう添える（ステップ 8 の下書きの対象に使う）

### 失敗したレビュー源の扱い

次のどれかに当たったレビュー源は**失敗**として扱い、指摘 0 件とは区別する。

- 起動できなかった（エージェントの呼び出しがエラーになった等。pr-review-toolkit が入っていないことは 3-0 で先に確かめる）
- エラーで終わった、または報告の形になっていない
- 今回の変更を見ていない（見たファイルの一覧にステップ 1 の変更ファイルが 1 つも無い、security-review が取った差分が空だった・今回の変更ファイルを含まない等）。変更ファイルをすべて見るはずの code-reviewer と仕様チェックは、一覧から 1 つでも欠けていれば失敗とする（削除されたファイルは作業ツリーに無く開けないので、欠けていても数えない）。観点を絞ったエージェント（#3〜#6）は関係のないファイルを開かないのが普通なので、一部が欠けていても失敗にしない
- 仕様チェックが仕様のファイルを読めていない（受け取ったファイルのうち 1 つでも、報告の冒頭の一覧に無い）。レビュー源欄には、どのファイルを読めていないかを書く

失敗したものはヘッダーのレビュー源欄に「失敗」と理由を書き分け、ボードを告げるときにチャットでも伝える。失敗と判定したレビュー源が指摘を返していれば、捨てずにボードに載せ、ほかの指摘と同じく検証する。固定の code-reviewer が失敗したときは、選択分だけで続けるか止めるかをユーザーに確認する。

### 仕様チェック（自前）の実行

サブエージェント（general-purpose）を 1 つ起動し、ほかのレビュー源と並列に走らせる。仕様が複数あっても、エージェントは 1 つにまとめる（仕様ごとに分けると同じ問題が重複して出る）。外部のレビュー源の結果は渡さない（独立して見る）。渡すもの:

- base と差分の取り方（ステップ 1）
- 受け取った仕様のすべて。ファイルはパスを渡す（sounding-board のボードなら**確定事項（「この設計から作るもの」を含む）と構造（Design Tree またはタイムライン）** を、プランファイルなら手順と変更対象を仕様として読むよう指示する。プランが決定を「ボード参照」で済ませていて、参照先のボードも渡されていれば、それも読む。読めない参照（渡されていないボードなど）があれば報告させる）。貼り付けた本文は、そのまま本文を渡す
- 見る観点: **仕様にあるのに実装されていない**／**仕様と違う形で実装されている**／**仕様に無い変更が入っている**。一般的なコード品質・スタイルは見ない（ほかのレビュー源の担当）。仕様どうしが食い違っていれば、どちらに合わせるかは決めずに、食い違いとして報告する
- 報告の形: 冒頭に読んだ仕様のファイルと見たファイルの一覧、続けて指摘ごとに 対象ファイル:行（実装が無い指摘は、入るはずだったファイル）・問題・根拠（どの仕様のどの記述か。ボードなら Q の ID、貼り付けの本文なら該当する一文）。コードは修正しない

仕様チェックが読めない参照を報告したら、ボードを告げるときに、その参照先（例: プランが参照しているボード）を渡すかを一言聞く。渡されたら、仕様に足して再レビューで使う。こちらから `.scratch/` などを探しには行かない（3-3）。

## ステップ 5: 統合・分類

### 重複の統合

複数のレビュー源が同じ箇所に実質同じ問題を指摘したら**統合して1件**にし、出典タグを併記する（例: `[spec] [code-reviewer]`）。統合するのは「同じ問題」だけであり、同じ行への別種の指摘は別件のまま残す。

出典タグはレビュー源の短い名前で書く: `code-reviewer` / `spec`（仕様チェック）/ `silent-failure` / `type-design` / `pr-test` / `comment` / `security-review`。ヘッダーのレビュー源欄も同じ名前にする（再レビューで「前回実行」を照らし合わせるため）。

### must / want / nits の判定基準（既定）

| 分類 | 基準 |
|---|---|
| **must** | バグ・セキュリティ・仕様違反・データ破壊。放置するとユーザー影響が出るもの |
| **want** | 設計・保守性・テスト欠落。動くが将来コストになるもの |
| **nits** | 命名・スタイル・好み。どちらでも動作も保守性も変わらないもの |

プロジェクトの CLAUDE.md 等に独自の基準・重み付けがあれば**そちらを優先**する（レビュー開始時に一度確認する）。

### ID の付番

must → `M1, M2, ...` / want → `W1, W2, ...` / nits → `N1, N2, ...`。再レビュー時は既存 ID を変えず、新規指摘に続番を振る。

**分類と ID はここで確定し、以後動かさない。** ステップ 7 の検証で見立てが変わっても、カードの移動や ID の振り直しはしない（ボードは検証前に表示済みで、ユーザーが既に ID を見ているため）。

## ステップ 6: ボード生成

同梱の `template.html` を原型に、単一 HTML として書き出す。構成:

- ヘッダー: 見出しは `レビュー: <ブランチ名> — <変更内容の一言>`（`<title>` も同じ。ブランチ名は `git branch --show-current`）。一言はファイル名の要約と同じ内容を日本語で短く書き、名前と同じく初回に決めて変えない。見出しの「レビュー:」は、ほかのスキル（review-triage の仕様の候補・board-to-impl のボードの候補からの除外、scratch-cleanup の片付け）がレビューボードを見分けるのに使い、ブランチは 2-1 の照合と scratch-cleanup（3-2。` — ` の手前までをブランチとして取る）に使うので、この形を崩さない。続けて最終更新（日時と何をしたか）・base（名前と merge-base の短縮ハッシュを必ず併記する。2-1 の照合と scratch-cleanup がどのリポジトリのボードかを見分けるのに使う）・コミット（先頭〜末尾の短縮ハッシュ）・レビュー源（実行したもの。失敗したものは理由つき）・仕様（受け取ったものをすべて。ファイルはパス、貼り付けは「貼り付けの本文（冒頭の一文: 〈…〉）」。仕様チェックを実行したとき）・サマリ（分類ごとの件数と、そのうち未定の件数）・推奨サマリ
- must / want / nits の3セクション。各指摘はカードで、ID・タイトル・対象（`ファイル:行`）・出典タグ・内容（結論1行＋必要なら補足1〜3文）・ステータス・推奨欄を持つ。「コメントする」「投稿済み」のカードには下書きの欄を置く（ステップ 8）
- ステータスは5値: **未定**（初期値）/ **コメントする** / **投稿済み** / **コメントしない** / **保留**
- この時点では検証前なので、新規指摘の推奨欄とヘッダーの推奨サマリは **「検証中」** にしておく

生成したら `open <フルパス>` でデフォルトブラウザに表示し、フルパスを告げる（macOS 以外では `xdg-open` 等に読み替える。開けない環境ならフルパスの告知だけで良い。open は初回と再レビュー開始時のみ。ステータス更新のたびに開き直さない）。あわせて「続けてコメントするかを検証します」と一言添え、**そのままステップ 7 に進む**。

## ステップ 7: コメントするかの検証

ボード生成後、**件数に関わらず常に実施する**（ユーザーに実施要否を問わない）。各指摘が作者にコメントする価値があるかをコードに当たって確かめ、推奨と理由をボードに載せる。

### 検証の深さ

**全件、対象コードを実際に読んで検証する**（must / want / nits を問わない）。指摘文だけで判定しない。確認する観点:

- **妥当性** — 指摘は事実か。呼び出し元・周辺コード・既存のガードを見て、誤検知でないか確かめる
- **実害** — 放置した場合に何が起きるか。その経路に実際に到達し得るか
- **やり取りの手間** — 作者が直す範囲と、指摘をめぐるやり取り（説明・反論・往復）にかかる手間

### 推奨の 3 値

基準は「**作者に直してもらう価値が、指摘のやり取りの手間に見合うか**」。直すのは自分ではなく作者なので、review-triage の「修正コストに見合うか」とは違う（検証の観点の 3 つめ・要判断の基準・再レビュー時の再検証の対象も review-triage と違う）。

| 推奨 | 基準 |
|---|---|
| **コメントする** | 指摘は事実で、実害または将来コストが、作者に直してもらう手間とやり取りに見合う |
| **コメントしない** | 誤検知、または事実だが作者に直してもらう価値がやり取りの手間に見合わない |
| **要判断** | 仕様の意図・チームの方針・作者との関係など、ユーザーにしか決められない情報に依存する。何が分かれば決まるかを理由に書く |

無理にどちらかへ倒さない。判断材料が足りないものは「要判断」にする。

### 理由の書き方

各推奨に**理由を 1 行**添える。検証で確認した事実を書く（「重要なのでコメントする」のような分類の言い換えは不可）。

- **誤検知**は「誤検知 — 根拠」と明記する（例: 「誤検知 — 呼び出し元 `foo.ts:40` で null を弾いており到達しない」）。**誤検知でもカードは消さず、元のセクションに残して「コメントしない」推奨とする**。黙って削ると、検証側の誤判定で本物の指摘が消えても誰も気付けない
- **分類とのずれ**は理由に明記する（例: 「実害なし、want 相当」「nits とされたが実際に例外になる、must 相当」）。分類と ID は動かさない（ステップ 5）。下書きのラベルは、この一行で読み替える（ステップ 8）

### 担い手の切り替え

| 検証対象の件数 | 担い手 |
|---|---|
| 10 件以下（目安） | 本体が直接検証する |
| それを超える | ファイル・ディレクトリ単位などで分割し、サブエージェント（general-purpose）を**1メッセージにまとめて並列起動**して検証させ、本体が結果を統合する |

サブエージェントには担当分の指摘（ID・対象・内容）と base・差分の取り方（ステップ 1）に加え、**上記の「検証の深さ」「推奨の 3 値」「理由の書き方」をそのまま渡す**。基準を渡さないと分割ごとに推奨の粒度がぶれる。「コードは修正しない・ID ごとに 推奨＋理由 1 行 を返す」ことも指示する。統合時、本体は粒度の揃っていない推奨を均す。サブエージェントが返さなかった ID や、推奨・理由が欠けた ID は、本体が対象コードを読んで検証して埋める（「検証中」のまま残さない・指摘文だけで埋めない）。

### ボードへの反映

検証が終わったらボードを上書きする。

- 各カードの推奨欄を「検証中」から **推奨＋理由** に置き換える
- ヘッダーの推奨サマリを内訳にする（例: 「推奨: コメントする 5 / コメントしない 12 / 要判断 2」）。must / want / nits の件数には誤検知ぶんも含まれたままなので、実質量はこのサマリで伝える
- **ステータスは「未定」のまま変えない**。推奨をステータスに反映するのはユーザーの ID 指示だけ
- `open` し直さず、一行で告知する（例: 「検証完了、ボード更新（推奨: コメントする 5 / コメントしない 12 / 要判断 2）。リロードしてください」）。「要判断」があれば、何を決めてほしいかをチャットでも短く挙げる

### 再レビュー時

検証するのは次の指摘だけ。それ以外は前回の推奨と理由を引き継ぐ。

- 新規の指摘
- ステータスが「未定」「保留」のままの指摘
- ステータスが「コメントする」でまだ投稿していない指摘。作者の push で行番号や中身が変わり得るので、指摘が残っていれば下書き（対象の行番号を含む）を作り直す。解消していたら作り直さず、推奨を「コメントしない（解消済み）」に変え、前回の下書きに「古い」と印を付ける。ステータスは変えず、ユーザーの指示を待つ

ステータスが「投稿済み」「コメントしない」の指摘は再検証しない（投稿済みの再発は 2-1 のとおり元のカードに書き足すだけ）。確定済みの判断と食い違う推奨を出してもノイズにしかならない。

## ステップ 8: 指示の受け付けと下書き

ユーザーはボードを見て **ID で指示**する（例: 「M1 と W2 コメントする、N は全部コメントしない」）。

- ID 指示を受けたら**ボードのステータスを更新**する（「コメントする」「コメントしない」「保留」を反映。ボードは毎回全体を上書きする）。コードは修正しない
- 「コメントする」にした指摘には、**その時点で下書きを作り**、カードに載せる（下の「下書きの決まり」）。別の指示は待たない
- ユーザーが PR に投稿したと伝えたら、その指摘を「投稿済み」にする。このスキルからは投稿を確かめられないので、伝えられたときだけ付ける。下書きは、投稿した内容の記録として残す
- 「コメントする」から「コメントしない」「保留」に変えたら、下書きを消す。あとで「コメントする」に戻したら、その時点のコードで作り直す
- 更新の告知は一行＋変更点の要約で良い（例: 「ボード更新（M1・W2 → コメントする・下書きを追加、N1〜N3 コメントしない）」）
- 指示が曖昧な場合（例: 「must だけコメントして」の対象に保留中が混ざる等）は解釈を確認してから反映する
- **推奨の一括承認は設けない**。「推奨どおりで」のような指示は曖昧な指示として扱い、反映する ID と内容を列挙して確認を取ってから反映する（「要判断」は一括の対象にできないので個別に問う）

### 下書きの決まり

下書きは、ユーザーが PR のコメント欄に写して投稿するためのもの。ボードのカードに、**対象**と **Markdown のままの本文**で載せる。

- **対象**: 差分の中にある HEAD の行への指摘は `ファイル:行`。次のものは「**PR 全体へのコメント**」とし、関係するファイル:行は本文に書く
  - 差分の外の行への指摘（多くのホスティングで行へのコメントにできない）
  - 実装が無い指摘（仕様チェックの「入るはずだったファイル」）
  - 削除された行（HEAD に無い行）への指摘。本文に「削除された `<ファイル>:<base 側の行>`」と書く
- **ラベル**: 本文の先頭に `[must]`・`[want]`・`[nits]` を付ける。ボードの分類どおりにするが、ステップ 7 の理由で分類とのずれを書いた指摘は、読み替えた分類のラベルにし、下書きの欄に「ボードの分類は must、下書きは want」のように注記する。ボードの分類と ID は動かさない
- **書き方の決まり**: プロジェクトの CLAUDE.md 等にコードレビューのコメントの書き方（ラベル・敬語・テンプレートなど）の決まりがあれば、そちらに従う
- **言語**: 受け取った仕様（PR の説明文など）やコミットメッセージの言語に合わせる。分からなければ会話の言語にする
- **本文**: 何が問題か・根拠（どの経路で何が起きるか、どの仕様のどの記述か）・提案を短く書く。作者が読んで直せるように、ボードの ID や推奨の理由の言い回しは持ち込まない

## 再レビューの流れ

作者が push した後にもう一度見るときは、ユーザーが手元のブランチを更新してから（pull など）起動し直す。ステップ 1 の確かめからやり直し、2-1 で同じボードを引き継ぐ。**レビュー源と仕様は再レビューでも毎回問う**。push で差分は前回と変わるため、前回の選択を無言で引き継がない。

## HTML を書くときの技術的な制約

sounding-board スキルと同じ制約に従う:

- 単一ファイルで完結（CSS はインライン `<style>`、外部リソースは読み込まない。JS は入れない）
- ダークモード対応（`prefers-color-scheme`。テンプレートの CSS 変数で自動的に満たされる）
- `lang="ja"`、`<meta charset="utf-8">`、viewport meta
- 更新は毎回全体を上書き（部分 Edit の継ぎ足しで構造を壊さない）。上書きの前に、いまのボードを読み直す（会話の文脈が要約されたあとに、カードや下書きを落として書き戻さないため）
- **CSS はテンプレートの `<style>` ブロックを丸ごと複製する**。スクリプトで正規表現抽出する場合は、行頭の `<style>` 行から `</style>` 行までを取る。冒頭コメントなどへの誤一致で CSS の先頭にゴミが混ざると、`:root` の変数定義ごと無効になり、色や線がすべて消える
- **書き出すたびに構造を確かめる**: `grep -c '<style' <file>` と `grep -c '<html' <file>` がどちらも 1 であること（誤抽出時はテンプレートの `<html>`・`<style>` が二重に入る）。満たさなければ作り直してから告知する

## やらないこと

- **コードの修正**（直すのは作者。自分のブランチを直すなら review-triage）
- **PR への投稿**・`gh` などホスティングの CLI の利用・PR の情報の取得（投稿は人がする）
- `git fetch`・worktree の作成・ブランチの checkout（手元の状態を確かめるだけ）
- 未コミットの変更があるまま・detached HEAD・upstream が無い・upstream と一致しないままのレビュー
- base の推定（引数に無ければ聞く）
- `.scratch/` からの仕様の候補探し（仕様はユーザーが渡したものだけ）
- **仕様チェック以外の自前レビュー**（一般的な観点・深さは外部のレビュー源に委譲する）
- **推奨のステータスへの無断反映**（推奨は判断材料。ステータスを動かすのはユーザーの ID 指示だけ）
- **検証による指摘の削除・分類変更・ID 振り直し**（誤検知も見立てのずれも、推奨の理由に書いて残す）
- **検証の省略・指摘文だけでの判定**（件数が少なくても多くても、全件コードを読む）
- 投稿済み・コメントしないの指摘の蒸し返し
