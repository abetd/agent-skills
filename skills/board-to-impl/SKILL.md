# board-to-impl

sounding-board で**凍結したボード**を出発点に、プランファイルを作って実装まで進める。途中で 3 回確認する。

| 確認 | いつ | 何を見るか |
|---|---|---|
| ① | プランを作る前 | ボードに不明点・矛盾が無いか |
| ② | プランを作ったあと | プランにボードからの漏れが無いか、ボードに無い手順が無いか |
| ③ | 実装したあと | 実装にプランからの漏れ・ずれ・不具合が無いか |

確認はどれも、**それぞれ新しいサブエージェント**に見させる。ボード・プラン・実装を同じセッションで書いていると、自分の書いたものの穴に気付きにくいため。見つかったものを直すのと、ユーザーに質問するのは本体が行う。

どの確認でも、**判断の要る問いがあれば勝手に進めず、止めてユーザーに聞く**。聞かずに直してよいのは次の 3 つだけ。

- 確認 ② で、直し方がボードから 1 つに決まるプランの直し（直したものは、実装の許可を求めるときに一覧で見せる → ステップ 5・6）
- 確認 ③ で、プラン（とボード）どおりに直せば済むもの（→ ステップ 8）
- 確認 ③ で、実装後に新しく落ちたテスト（→ ステップ 8）

確認や実装の途中で出た答えが設計の決定に当たるときは、どの場面でもボードに書き戻す（→ 3-1）。

---

## ステップ 1: ボードを決める

1. 引数でボードが渡されていればそれを使う（ファイル名だけなら、2 の置き場所から探す）
2. 無ければ、リポジトリルート（`git rev-parse --show-toplevel`）の `.scratch/`（無ければセッションの scratchpad）の直下（`archive/` などの下は見ない）から、凍結済みの sounding-board のボードを集め、更新日時の新しい順に**最大 4 つ**を AskUserQuestion で選ばせる（label はファイル名、description は更新日時とヘッダーのテーマ）。候補が 1 つだけのときは、選択肢に「やめる」を足して 2 択にする（AskUserQuestion は選択肢が 2 つ以上要る。黙ってその 1 つを使わない）。1 つも無ければ、凍結済みのボードが無いと告げて終える

sounding-board のボードの見分け方:

- review-triage のボード（ヘッダーの見出しが `レビュー:` で始まる）ではない
- explainer の説明資料ではない（sounding-board のボードはテンプレートの `<style>` を丸ごと複製しているので、完了バナーの CSS 定義 `.done{` を持つ。説明資料は持たない）

**凍結の判定**: `<header>` 内のコメントの外に完了バナー `<div class="done">` があれば凍結済み。テンプレートは凍結前でもコメントの中にバナーを持つので、コメントの中にあるものは数えない。`.done{...}` の CSS 定義も数えない。

凍結されていないボードを渡されたら、**止めて終える**。回答待ち・未着手が残っているので、sounding-board で詰め切って凍結してから、もう一度起動するよう案内する。このスキルの中で残りの問いを詰めない（sounding-board の役割まで持たない）。

## ステップ 2: 再開かを確かめる

プランファイルはボードと同じディレクトリに置き、名前は `<ボード名>-plan.md`（`<ボード名>` はボードのファイル名から `.html` を除いたもの）。追加のプランは `<ボード名>-plan-2.md`、`-plan-3.md` … と連番にする。

ボードと同じディレクトリに、このボードのプラン（`<ボード名>-plan.md`・`<ボード名>-plan-<連番>.md`）があるかを見る。

- **無い**: 新しく始める。ステップ 3 へ
- **いちばん新しい連番のプランに、チェックの付いていない手順が残っている**: 途中からの再開。プランのパスと残りの手順を示し、続きから実装してよいかを聞く。許可が出たらステップ 7 の実装から続ける（確認 ① ② はやり直さない）。プランの「基準」の節に記録が無ければ、先に基準を取る（ステップ 7）
- **すべてチェック済み**: そのプランの実装は終わっている。追加の依頼として新しいプラン（次の連番）を作るか、やめるかを聞く。作るなら、何を足すのか（ボードを詰め直して増えた決定・ユーザーからの依頼）を確かめてからステップ 3 へ進む。新しいプランには、まだ実装していない分だけを書く

## ステップ 3: 確認 ①（ボードを点検する）

新しいサブエージェント（general-purpose）を 1 つ起動する。渡すもの:

- ボードのパス。**全体を読む**よう指示する（確定事項・「この設計から作るもの」・Design Tree・Q&A の補足・Q&A ログ）
- 見る観点:
  - **不明点** — 実装するのに決まっていないこと、読む人によって解釈が分かれる書き方
  - **矛盾** — 確定事項・Design Tree・「作るもの」・Q&A ログのあいだで食い違っていること。「作るもの」に対応する決定が無い、決定に対応する「作るもの」が無いことも含む
  - **前提の食い違い** — ボードが前提にしている事実（ファイルの有無・既存実装の挙動など）が、今のコードと合わないこと
- 報告の形: 冒頭に読んだファイルの一覧、続けて問いごとに ID（`C1`, `C2`, …）・箇所（ボードの決定の ID）・内容・実装の前に決める必要がある理由・考えられる答え。何も無ければ「なし」と返す。ファイルは書き換えない

本体は、返ってきた問いをボードと照らし合わせる。ボードの別の箇所に答えが書いてあるものだけは、その箇所を示して問いから外してよい。それ以外は**止めてユーザーに聞く**。

- 問いは AskUserQuestion で出す。1 回に 1〜4 問、選択肢は 2〜4 つ。推奨できるものは label の末尾に「（推奨）」を付けて先頭に置く
- 答えが選択肢に収まらなかったら、確定扱いにせず、調べて答えるか問いを分けてから改めて聞く

### 3-1. 答えをボードに書き戻す

確認 ① の答えは**ボードに書き戻す**（プランには書かない）。確認 ②・実装中・確認 ③ で出た答えも、設計の決定に当たるものはここに従って書き戻す。review-triage の仕様チェックはボードを読むので、ボードが古いままだと、ボードに無い決定どおりの実装が仕様違反として指摘される。

- Q&A ログの末尾に `Round N — board-to-impl での確認（確認 ①）` の Round を足し、問いと答えを載せる（括弧の中は、確認 ②・実装中・確認 ③ のどこで出た問いか）。確定事項を書き直し、Design Tree の該当ノードも直す。今回変わった項目にだけ `NEW` を付け、前の `NEW` は外す
- **凍結は保つ**。完了バナーはコメントの外に残し、確定項目数が変わったら書き直す
- 書き方は sounding-board の「HTML を書くときの技術的な制約」に従う: 書く前にボードを全文読み直す／毎回全体を上書きする／`<style>` ブロックは今のボードのものをそのまま残す／書き出したら `grep -c '<style' <file>` と `grep -c '<html' <file>` がどちらも 1 であることを確かめる

**設計を大きく変える答え**（既存の決定を覆す・「作るもの」が増減する・新しい論点が生まれる）なら、書き戻さずに**止めて終える**。sounding-board で凍結を解いて詰め直し、もう一度凍結してから起動し直すよう案内する。

## ステップ 4: プランを作る

`<ボード名>-plan.md`（再開で追加のときは次の連番）を、ボードと同じディレクトリに書く。

```markdown
# <ボードのテーマ> — 実装プラン

設計と決定事項: [<ボードのファイル名>](./<ボードのファイル名>)（詳細は sounding-board のボード参照）

## <まとまりの見出し>

- [ ] `<変更するファイル>`: <何をするか>（Q3・Q5）
- [ ] …

## 基準

（ステップ 7 で書く）
```

- 冒頭にボードへのリンクを置き、決定の中身は「ボード参照」で短く保つ（sounding-board の「プランファイルとの関係」）
- **手順ごとに、もとになったボードの決定の ID を書く**（確定事項の ID。`Q3`・`前提1` など）。確認 ② はこの ID で照合する
- ボードの決定から直接は出てこないが、必要な手順（リポジトリの規約で求められる README の更新など）は、ID の代わりに `（付随: <理由>）` と書く
- 見出しは変更のまとまり（スキル・モジュール・ドキュメントなど）で切る。手順はチェックボックスにし、実装しながら付ける

## ステップ 5: 確認 ②（プランとボードを照合する）

新しいサブエージェント（general-purpose）を 1 つ起動する。確認 ① のサブエージェントは使い回さない。渡すもの:

- ボードのパスとプランのパス。追加のプラン（`-plan-2.md` 以降）なら、それまでのプランのパスも渡し、実装済みの分は漏れに数えないよう指示する
- 見る観点（**両方向**）:
  - **漏れ** — ボードの確定事項・「この設計から作るもの」の各項目が、プランのどの手順にも対応していない
  - **ボードに無い手順** — 手順に決定の ID が無い、または書かれた ID の決定と手順の中身が合わない。`（付随: …）` の手順は、理由が成り立つかを見る
  - **ずれ** — 手順がボードの決定と違う形になっている
- 報告の形: 冒頭に読んだファイルの一覧、続けて指摘ごとに 種類（漏れ／ボードに無い手順／ずれ）・決定の ID または手順・内容・直し方がボードから 1 つに決まるか。何も無ければ「なし」と返す。ファイルは書き換えない

本体の扱い:

- **直し方がボードから 1 つに決まるもの**（漏れた手順を足す・ID を直す・ずれた手順をボードどおりに書き直す）は、プランを直す。直したものはステップ 6 で一覧にして見せる
- **判断が要るもの**（ボードのどの決定にも当たらない手順を残すか、ボードの書き方では手順が決まらない等）は、止めてユーザーに聞く。答えが設計の決定に当たるなら、3-1 に従ってボードに書き戻す（大きく変えるなら止めて sounding-board へ）

## ステップ 6: 実装を始める許可を取る

プランのパスと要約（まとまりごとの手順の数・変更するファイル）、確認 ② で直したものの一覧を示し、**実装を始めてよいかを聞く**。許可が出るまで実装しない。

## ステップ 7: 基準を取って実装する

### 基準

実装の前に、リポジトリにある確認手段（テスト・lint・ビルドなど。`package.json` の scripts・`Makefile`・言語の標準のテストコマンドなどから探す）を一度走らせる。結果をプランの「基準」の節に書く。

- 走らせたコマンドと、落ちたもの（テスト名など）。全部通ったならその旨
- 実装を始める時点の `git rev-parse HEAD` と、`git status --short` に出ていたファイル（確認 ③ で、実装による変更とそれ以前の変更を分けるため）

確認手段が無いとき、または基準を取る段階で動かない（ビルドが壊れている・環境のせいで動かない等）ときは、その旨を「基準」の節に書き、ユーザーにも伝える。確認 ③ のテストの比較はできなくなる。

### 実装

- プランの順に実装し、終わった手順からチェックボックスを付ける。**進捗はプランに付け、ボードには書かない**
- プランに無い判断が要る場面に当たったら、止めてユーザーに聞く。答えが設計の決定に当たるなら、3-1 に従ってボードに書き戻し、プランにも手順として足す
- **コミットはしない**

## ステップ 8: 確認 ③（実装とプランを照合する）

本体が、基準と同じ確認手段をもう一度走らせる。基準と比べて**新しく落ちたもの**を控える（もとから落ちていたものは対象にしない。直すとプランに無い変更が入るため）。

続けて、新しいサブエージェント（general-purpose）を 1 つ起動する。渡すもの:

- ボードのパスとプランのパス
- 実装の差分の取り方: `git diff <基準の HEAD> -- ':/' ':(top,exclude).scratch'` と、未追跡のファイル（`git ls-files --others --exclude-standard --full-name -- ':/' ':(top,exclude).scratch'`）。基準の時点で `git status --short` に出ていたファイルは、実装より前からの変更を含むことも伝える
- 新しく落ちたテストの一覧
- 見る観点:
  - **漏れ** — プランの手順（チェックの有無を問わない）が実装されていない、または一部しか実装されていない。チェックの付いていない手順が残っていれば、それも報告する
  - **ずれ** — プラン・ボードと違う形で実装されている
  - **不具合** — 実装した箇所が、プランの意図どおりに動かない（新しく落ちたテストの原因を含む）
  - 一般的なコード品質・スタイルは見ない（review-triage に任せる）
- 報告の形: 冒頭に読んだファイルの一覧、続けて指摘ごとに 対象ファイル:行（実装が無い指摘は、入るはずだったファイル）・種類・内容・根拠（プランの手順と決定の ID）・**分類**（下の表）。何も無ければ「なし」と返す。ファイルは書き換えない

| 分類 | 当たるもの | 本体の扱い |
|---|---|---|
| **直せる** | プラン（とボード）に書いてあるのに無い・違うもの。新しく落ちたテストで、直し方がプランから 1 つに決まるもの | **聞かずに直す** |
| **要判断** | プランとボードが食い違う、プランに無い設計の選択が要る、テストの期待とボードの決定が食い違う | **止めてユーザーに聞く** |

本体は、指摘ごとに対象コードを読んで事実かを確かめる。誤検知（既にある・別の箇所で満たしている）は根拠を添えて外す。分類が違うと見たら、聞かない側（直せる）へは倒さない。迷ったら要判断にする。

### 直して、もう一度確かめる

1. 「直せる」をすべて直す。「要判断」は止めてユーザーに聞き、答えに沿って直す（設計の決定に当たる答えは、3-1 に従ってボードに書き戻す）
2. 直したら、確認手段を走らせ直し、**新しいサブエージェント**で確認 ③ をもう一度回す
3. **2 回直しても残るもの**は、それ以上直さずに止めて、ユーザーに聞く（直しては壊すを繰り返さないため）。確認 ③ が走るのは、初回と再確認 2 回の最大 3 回

確認 ③ で何も残らなくなったら、ステップ 9 へ。

## ステップ 9: 終わりの報告

チャットで次を伝える。

- 実装した手順（プランのパスと、チェックの付いた手順の数）
- 確認 ③ で聞かずに直したものの一覧（指摘の内容と直した箇所）
- ユーザーに聞いて決めたこと、まだ残っている問い
- 基準と比べた確認手段の結果（確認手段が無かった・動かなかったときはその旨）
- 次にできること: コミットするか、review-triage でレビューするか（仕様にはボードとプランの両方を選べる）。**どちらもこのスキルからは始めない**

## やらないこと

- 凍結前のボードからの実装（sounding-board で凍結してから）
- 確認 ① ② ③ の省略、本体だけでの確認（それぞれ新しいサブエージェントに見させる）
- 判断の要る問いを、聞かずに決めて進めること（聞かずに直してよいのは、冒頭に挙げた 3 つだけ）
- 確認や実装の途中で出た設計の決定を、ボードに書き戻さずにプランだけに残すこと
- 許可前の実装
- 進捗をボードに書くこと（進捗はプランのチェックボックス）
- 基準の時点から落ちていたテストを直すこと（プランに無い変更になる）
- 一般的なコードレビュー（review-triage に任せる）
- コミット（ユーザーが明示的に頼んだときだけ）
