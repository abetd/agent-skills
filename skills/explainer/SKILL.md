# explainer

トピックを**何も知らない人**に向けて、**大きな絵と少ない言葉**で説明する HTML を 1 枚書き、ローカルに残す。

- 読み手は、自分（よく知らないことを理解したい）か、他の人（説明して分かってもらいたい）
- 説明資料はローカルの単一 HTML として残す。**Artifact として公開しない**。`.scratch/` に置けば、ほかのスキルのボードと同じ場所で後から見返せる

---

## ステップ 1: トピックを確定する

引数や依頼文からトピックを取る。無ければ会話の文脈から推測する（ステップ 3 の確認で示すので、ここで別に聞かない）。

トピックがこのリポジトリのコード・設定・環境に関わるなら、**先に調べてから書く**。推測で絵を描かない。

## ステップ 2: 出力先とファイル名を決める

### 2-1. 出力ディレクトリ

1. リポジトリルート（`git rev-parse --show-toplevel`）に `.scratch/` があればそこ
2. git リポジトリの中で `.scratch/` が無ければ、ステップ 3 の確認で作るかも一緒に聞く。作るが選ばれたら、リポジトリルート直下に作ってそこに置く
3. 作らないが選ばれたとき・git リポジトリの外のときは、セッションの scratchpad ディレクトリ

`.scratch/` は作業場で、git で管理するかは利用者に任せる。作るかを聞くときの決まり:

- 断られても記録しない。次に起動したときに `.scratch/` が無ければ、また聞く
- git リポジトリの外では聞かない（作る場所の基準が無い）
- 作るのは実ディレクトリだけ（`mkdir <リポジトリルート>/.scratch`）。symlink にするかどうかはユーザーに任せる
- git に無視されているかは確かめず、`.gitignore` なども書き換えない（git で管理するかは利用者が決める）

### 2-2. ファイル名

`<トピック>-explainer.html`。`<トピック>` は短い英語の kebab-case にする（例: 「DNS のしくみ」→ `dns-explainer.html`）。

プロジェクトの CLAUDE.md 等に**プランファイル等のプレフィックス命名規則**（チケット番号・Issue 番号など）があれば、先頭にそのプレフィックスを付ける（例: `PROJ-123-dns-explainer.html`・`42-dns-explainer.html`）。

### 2-3. 同名ファイルが既にあるとき

- **この会話で自分が書いたファイル**なら、手直しなので上書きする
- そうでなければ上書きせず、連番を付けて別ファイルにする（`dns-explainer-2.html`、それもあれば `-3` …）。過去の説明を黙って消さない

## ステップ 3: 作る前に確認する

新しい説明資料を作る前に、**毎回** AskUserQuestion で確認する（`/explainer` で起動したときも）。

- 問いの文にトピックと書き出し先のファイル名を入れる（例: 「『DNS のしくみ』を説明資料にしますか？（`.scratch/dns-explainer.html`）」）
- 選択肢は「説明資料にする」と「チャットで答える」の 2 つ
- 2-1 で `.scratch/` を作るかを聞くときは、「説明資料にする」を「`.scratch/` を作って説明資料にする」と「scratchpad に置いて説明資料にする」の 2 つに分け、選択肢を 3 つにする。scratchpad の方の description には、セッションが終わると辿り着けなくなることを書く
- 「チャットで答える」が選ばれたら、このスキルを終えて普通にチャットで答える
- トピックやファイル名の修正が返ってきたら、それを反映して進める

同じ会話で書いた説明資料の手直し（2-3 で上書きになるもの）は確認しない。

## ステップ 4: デザインの指針を決める

### 4-1. artifact-design が使えるとき

利用可能なスキルに `artifact-design`（Artifact 用のデザイン指針）があれば、**Skill ツールで読み込み**、その指針でデザインする。配色・書体・レイアウトをトピックごとに決めるので、テンプレート（`template.html`）は使わない。

artifact-design は claude.ai に公開する Artifact 向けに書かれているので、次のとおり読み替える。**この SKILL.md の指示が artifact-design より優先する。**

| artifact-design の記述 | explainer での扱い |
|---|---|
| publish する・Artifact ツールを呼ぶ | **しない**。quickstart も呼ばない。ローカルにファイルを書くだけ |
| `<!doctype>`・`<html>`・`<head>`・`<body>` を書かない（公開時に包まれる） | ローカルのファイルなので**自分で書く** |
| CDN のスクリプト・Google Fonts を読み込める | **読み込まない**。HTML を他の人に共有しても同じように見えるよう、書体は一般的なシステムフォントだけにする（下の書体の表）。JS・CDN のスクリプト・画像も使わない |
| 見出し用・本文用・補助の書体を組み合わせる | 組み合わせ方はそのまま従い、選ぶ範囲をシステムフォントのゴシック・明朝・等幅にする。基本はゴシック |
| mermaid が自動で描かれる | Artifact の画面でしか動かないので**使わない**。図はインライン SVG で描く |
| 仕上げ前に ArtifactCheck で一度見る | **しない**。見た目はステップ 7 でユーザーがブラウザで見る |
| 明暗の配色を CSS 変数で設計する | そのまま従う。SVG の色も CSS 変数から取る（色コードを直書きしない） |

システムフォントは Mac と Windows で書体名が違うので、両方を並べて指定する。

| 系統 | `font-family` の例 |
|---|---|
| ゴシック | `-apple-system, BlinkMacSystemFont, "Hiragino Sans", "Hiragino Kaku Gothic ProN", "Yu Gothic", YuGothic, Meiryo, sans-serif` |
| 明朝 | `"Hiragino Mincho ProN", "Yu Mincho", YuMincho, serif` |
| 等幅 | `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` |

ステップ 5 の書き方・見せ方は、artifact-design を使うときもそのまま守る（絵が主役であることは explainer の決まり）。

### 4-2. artifact-design が使えないとき

同梱の `template.html` を原型にし、ステップ 5 の指針で組む。テンプレートが持つのは**配色と文字の基本、少しの汎用部品**だけで、レイアウトや並び順は持たない。

| テンプレートの中身 | 扱い |
|---|---|
| 色トークン（`--c1`〜`--c4` ほか）・ダークモード | そのまま使う |
| 文字・余白の基本 | そのまま使う |
| 汎用の最小部品（`.panel`・`.grid`・`.caption`） | 使わなくてよい |
| SVG 用クラス（`.fill-*`・`.stroke-*`・`.label`） | 絵の色はここから選ぶ |

- レイアウトに必要な CSS は、`<style>` 末尾の「ここから下はトピックごとに足す」の下に足す。色は必ず `var(--…)` から選ぶ
- 色に役割を持たせる（CSS 変数のコメントを参照: 主役・相手役・うまくいく・問題）
- **CSS はテンプレートの `<style>` ブロックを丸ごと複製する**。スクリプトで正規表現抽出する場合は、行頭の `<style>` 行から `</style>` 行までを取る。冒頭コメントなどへの誤一致で CSS の先頭にゴミが混ざると、`:root` の変数定義ごと無効になり、色がすべて消える
- テンプレートの使い方コメントと SVG の書き方の例は、出力には残さない

## ステップ 5: 中身を組み立てる

### 5-1. 書き方

- **絵が主役、言葉は脇役**。1 枚の絵に添える文は一文、多くても二文
- **1 枚の絵に 1 つのことだけ**描く。言いたいことが増えたら絵を分ける
- 専門用語は使わない。どうしても要るなら、たとえ（身近なもの）と一緒に出す
- 冒頭に「何の話か」を一文で置く。それ以外の構成は決めない（まとめも、効くときだけ置く）。だらだら長くしない
- 文章は会話の言語で書く

### 5-2. 見せ方を選ぶ

**まずトピックの型を見極め、それに合う見せ方でレイアウトから組み立てる**。毎回同じ並びにしない。

| トピックの型 | 見せ方の例 |
|---|---|
| 仕組み・流れ | 左から右への流れ図、コマ送り |
| 比較・違い | 左右（または表裏）に並べて対比する |
| 構造・部品 | 全体図を 1 枚描き、部分に吹き出しを付ける |
| 時間の変化 | タイムライン、before / after |
| 量・割合・規模 | 大きさ・面積・本数の違いで見せる |

複数の型にまたがるトピックなら、型ごとに絵を分けて組み合わせる。表は出発点であって拘束ではない。たとえ（身近なものへの置き換え）は、どの型でも効くときに添える。

### 5-3. 絵の描き方

- 絵は**インライン SVG** で描く。画像ファイルは使わない
- 色は CSS 変数（テンプレートなら SVG 用クラス）から取る。色コードを直書きすると、ダークモードで色が切り替わらない
- 同じものは全部の絵で同じ色にする
- 形は単純に（丸・角丸の四角・矢印・アイコン程度）。描き込みより、配置と大きさで関係を見せる
- 文字や図形が重ならず、viewBox の内側に収まるように置く
- SVG には `role="img"` と、絵の中身を一文で表す `aria-label` を付ける

## ステップ 6: 書き出して確かめる

### 6-1. HTML の技術的な制約

- **単一ファイルで完結させる**。CSS はインライン `<style>`、外部リソース（CDN、Web フォント、画像）は読み込まない。JS は入れない
- **ダークモード対応**（`prefers-color-scheme`）
- `<html>` の `lang` は文章の言語に合わせる。`<meta charset="utf-8">`、viewport meta を付ける
- スマホ幅（約 400px）でも横スクロールが出ないようにする

### 6-2. 構造を確かめる

書き出すたびに `grep -c '<style' <file>` と `grep -c '<html' <file>` がどちらも 1 であることを確かめる（テンプレートの誤抽出などで二重に入っていないか）。満たさなければ作り直す。

見た目はスクリーンショットで確かめない。ステップ 7 で開いた HTML をユーザーが見て、崩れていれば直しを頼む。

## ステップ 7: 表示と告知

- **新しいファイルを書いたとき**は、フルパスを告げ、`open <フルパス>` でデフォルトブラウザに表示する（macOS 以外では `xdg-open` 等に読み替える。開けない環境ならフルパスの告知だけで良い）。scratchpad に置いたときは、「リポジトリの外に置いたので、セッションが終わると辿り着けなくなる」ことも伝える
- **手直しで上書きしたとき**は `open` し直さず、一行で何を変えたかを告げる（ブラウザ側はリロードで最新になる）

## やらないこと

- Artifact としての公開・Artifact ツールの呼び出し（ローカルファイルに留める）
- 確認を取らずに新しい説明資料を作ること
- 外部リソース（Web フォントを含む）・JS の読み込み
- 調べれば分かることを推測で描くこと
- 別の機会に書かれた説明資料の上書き
- 議論や決定事項の可視化（sounding-board などの役割）
- `.done` というクラス名を CSS に定義すること（scratch-cleanup は `.done{` の有無で sounding-board のボードと説明資料を見分ける）
